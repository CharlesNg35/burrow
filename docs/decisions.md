# Decisions

Short records. Newest last.

## D1. Transport: raw TCP with a data-channel pool, no HTTP/2 or QUIC as primary

HTTP/2 only lets the client open streams, so the server could not open one per visitor without a control-channel round trip anyway. It also puts every stream behind one TCP connection (head-of-line blocking), has no UDP, and brings a large pre-auth surface (HPACK, SETTINGS, flow control). QUIC is a possible future option if UDP performance matters, but it would add a large dependency and its own TLS. Default: one TCP control channel per client plus one TCP data channel per visitor connection, taken from a pre-established pool.

## D2. Pool per client, not per service

rathole keeps 8 idle channels per TCP service. Because burrow tells the data channel its target in the first frame, any idle channel can serve any service of that client. Default `pool.min_idle: 4`, adaptive up to `pool.max_idle: 64`: when a visitor finds the pool empty, the target idle count doubles; it decays by one each idle minute.

## D3. Noise_NNpsk0_25519_ChaChaPoly_BLAKE2s, one handshake per channel

Every control and data channel runs its own handshake. A full handshake (both sides, one core) costs about 118 us (benches/cipher.rs), which the pool hides from visitors. Details and proof points are in docs/protocol.md.

## D4. Cipher: ChaChaPoly default, AES-GCM opt-in, `ring` backend

Measured on an i5-12600K (AES-NI, VAES, AVX2), seal plus open in one thread (`cargo bench --bench cipher`):

| backend    | cipher      | 16 KiB chunk | 64 KiB chunk |
| ---------- | ----------- | ------------ | ------------ |
| ring       | ChaChaPoly  | 1286 MiB/s   | 1261 MiB/s   |
| ring       | AES-256-GCM | 4591 MiB/s   | 4360 MiB/s   |
| RustCrypto | ChaChaPoly  | 810 MiB/s    | 833 MiB/s    |
| RustCrypto | AES-256-GCM | 864 MiB/s    | 853 MiB/s    |

snow enables `ring` through its `std` feature anyway, so using the `ring-accelerated` resolver adds no new crates. ChaChaPoly stays the default because it is constant-time on every CPU, including ARM boards without AES instructions. A client can set `cipher: aes-gcm` to get about 3.5x on x86 servers. The server accepts both; the choice is bound into the Noise prologue.

## D5. Config parsing: saphyr-parser for YAML and JSON, our own schema checker

serde_yaml is deprecated (0.9.34+deprecated), serde_yml has had soundness and maintenance concerns, and both stop at the first error. saphyr-parser is maintained (pushed 2026-10) and gives byte, line and column markers for every event. JSON is valid YAML 1.2 flow syntax, so the same parser builds the spanned tree for both; `.json` files are first checked with serde_json so JSON-only syntax errors are reported exactly. The structural check is driven by the JSON Schema that schemars derives from the config types, so `burrow schema`, editor validation and `burrow validate` share one definition. After the tree passes, serde (with `deny_unknown_fields`) builds the typed config.

## D6. One validation engine, run everywhere

`burrow server` and `burrow client` run the same checks as `burrow validate` before opening any socket, and the server runs them on every reload. Errors are printed in the same format each time. `burrow validate` is the same engine without starting anything.

## D7. Durations as integer seconds with a `_secs` suffix

No duration-parsing crate, and the unit is obvious from the key.

## D8. Heartbeat interval is server-owned

The server sends its heartbeat interval in the welcome message. The client times out after three missed intervals, so the two sides cannot disagree.

## D9. Insecure plaintext still authenticates

With `insecure_plaintext: true` on both sides, the Noise handshake still runs (so the secret is never exposed and auth stays strong), but data channels copy raw bytes after Connect and Status. The flag is part of the authenticated prologue, and a mismatch is refused after authentication with `Bye` reason plaintext mismatch. Raw bytes carry the end of each direction as a TCP FIN, so when a target closes first the client sends the first FIN on the data channel and holds its TIME_WAIT, unlike encrypted channels, where the server closes first. A client that sustains several hundred such connections per second can run out of local ports; use encrypted mode there, or allow reuse with `net.ipv4.tcp_tw_reuse=1` on Linux.

## D10. Data plane: data-channel pool, not a multiplexed connection

Evidence from code: frp turns yamux on by default (`tcpMux: true`), and chisel multiplexes SSH channels on one WebSocket. Both put every visitor behind one TCP flow-control window. rathole, like burrow, uses one TCP connection per visitor.

Evidence from measurement (docs/benchmark.md): frp is the cleanest experiment, because multiplexing can be switched off in the same code. Without tcpMux, frp's 4-stream throughput rises from 8.8 to 36.0 Gbit/s and its p99 echo latency under a 2 Gbit/s background load drops from 678 to 383 µs (head-of-line blocking gone), but new connections per second fall from 10.0k to 2.9k, because each visitor waits for a fresh TLS connection. A pre-opened pool keeps the first benefit without the second cost: burrow does 33.4 Gbit/s, a p99 of 549 µs under the same load, and 13.5k connections/s.

## D11. Record size: full 64 KiB Noise records for bulk data

Measured with `bench/run.sh` (burrow only, 2 runs each). Single-stream iperf3 through the tunnel: 8 KiB chunks 7.7 Gbit/s, 16 KiB 10.1, 32 KiB 12.2, 65519 B (largest Noise message) 12.8. With 4 streams: 23.0, 28.5, 32.8, 34.7. Small-message latency was unchanged (p50 61 µs in every case) because short reads are sealed from a 512-byte stack buffer. Big buffers exist only while data is flowing: a pump drops them when the socket has no data ready, so idle connections hold no large buffers.

## D12. Allocator: system malloc, except on musl

With mimalloc: throughput unchanged (12.6 vs 12.8 Gbit/s single stream), new connections per second +3% (14.1k vs 13.7k), but RSS with 10k idle connections rose from 167 MB to 273 MB. The cost outweighs the gain, so glibc, macOS, Windows and FreeBSD builds keep the system allocator.

The release Linux binaries are static musl builds, and musl's mallocng fragments under connection churn: in a soak the RSS of a server grew from 6.3 to 16.2 MB in under 2 hours while its live heap stayed at about 1.4 MB. Musl builds therefore use jemalloc (x86_64, aarch64 with 64 KiB pages allowed, riscv64), and mimalloc on 32-bit ARM, where jemalloc does not build with zig. With them the same soak stays flat.

## D13. insecure_plaintext copy path

`tokio::io::copy` uses an 8 KiB buffer: 14 Gbit/s single stream, behind rathole's plain TCP (16). A 64 KiB buffer reached 33 Gbit/s (69 with 4 streams), but a `BufReader` would hold 64 KiB per direction for the life of the connection (about 2.6 GB at 10k idle connections). The raw pump therefore uses the same lazy scheme as the encrypted path. Same throughput, and 10k idle connections cost 172 MB, the same as encrypted mode. The 128 KiB record-reader buffer is also freed once the plaintext stream takes over.

## D14. Listen backlog 4096

std and mio listen with a backlog of 128. A burst of 300 visitors overflowed it (`TcpExtListenOverflows`, "Possible SYN flooding" in dmesg), and some visitors were reset. All listeners are now created with a backlog of 4096, capped by the kernel's `somaxconn`.

## D15. Deferred: pinned-key NK mode and WebSocket transport

NK with a pinned server key plus an inner token would be a second authentication mode next to NNpsk0, which already authenticates both sides without extra key material. Not worth the extra security surface. A WebSocket-over-TLS transport needs rustls, webpki roots and tungstenite on the client, roughly doubling the dependency tree and the pre-auth parsing surface, for networks that only allow HTTPS. HTTP CONNECT and SOCKS5 proxy support already covers many restricted networks. Both stay out until there is a concrete need. The transport is isolated in `handshake.rs` and `src/transport/`, so either can be added later behind a config option. WebSocket was added later, see D17.

## D16. Leak hardening

Long-running behaviour is tested by state, not only by RSS. `tests/heavy.rs` churns TCP connections, UDP peers, client reconnects and reloads, and asserts that sessions, waiting visitors, UDP peers, open file descriptors and live tokio tasks return to their baseline after every round. This found and fixed: control-channel writer tasks that outlived a timed-out session, UDP relay tasks orphaned when their future was cancelled, stale pool waiters, client data channels that survived a client stop, and UDP peers that expired while traffic still flowed in one direction.

## D17. WebSocket transport, opt-in

Some servers can only be reached through an HTTP(S) reverse proxy or a CDN. For those, clients connect over WebSocket (RFC 6455) instead of raw TCP. The feature is off unless the server config has a `websocket` section, and a server configured for WebSocket only opens no TCP control port.

- **WebSocket over HTTP/1.1, not HTTP/2 streams or gRPC.** It passes through every common proxy and through Cloudflare. HTTP/2 extended CONNECT (RFC 8441) is rarely supported by proxies.
- **One WebSocket per data channel, taken from the same pool.** This keeps the head-of-line properties of D10. shellcn multiplexes yamux over a single WebSocket; burrow does not.
- **Noise runs inside the WebSocket.** A TLS-terminating proxy only sees Noise records, and the URL, path and headers grant nothing.
- **No MASQUE (RFC 9298).** CONNECT-UDP needs an HTTP proxy that relays UDP itself, mostly over HTTP/3. burrow already carries each datagram as its own record inside a data channel, so UDP services work over WebSocket unchanged, with the usual UDP-over-TCP latency on packet loss.
- **Keepalive.** Proxies close idle WebSockets (nginx after 60 s by default, Cloudflare after 100 s), and some only count data frames. The server therefore sends an encrypted keepalive record on idle pooled channels every 25 s. A test with an idle-killing proxy fails without it.
- **Crate: tokio-websockets 0.13** (strict RFC compliance, maintained, can use the `ring` backend burrow already ships), plus tokio-rustls, webpki-roots and httparse. The request head is parsed before the upgrade, so wrong paths are refused with 404 and nothing else is exposed.
- **Optional own TLS** (`websocket.tls.cert`/`key`), for servers without a proxy. Clients trust the public roots plus an optional `ca` file.
- **Cost, measured** (docs/benchmark.md, loopback): about 93% of the TCP throughput (11.75 vs 12.62 Gbit/s single stream), 12.0k vs 13.5k new connections per second, and about 1.8x the idle memory at 10k connections (391 vs 220 MiB), from the library's per-connection frame buffers. That is still well below frp (796 MiB) and chisel (719 MiB), which also uses WebSocket.

## D18. Reconnect: never give up by default

Clients retry forever with jittered backoff (250 ms up to 30 s, reset after 10 s of stable connection). DNS is re-resolved on every attempt, so moving the server and updating DNS needs no client change. Addresses are dialed with Happy Eyeballs (RFC 8305: interleaved families, the next attempt 250 ms after the previous one, first success wins), so a stale or black-holed address costs 250 ms instead of the whole connect timeout. An address that accepts TCP but then fails the TLS, WebSocket or Noise step (a load balancer with no backend, an address now used by another host) is tried last from then on, and the address of the last good handshake is tried first, so data channels follow the control channel. During an outage the client logs the first failure and then a summary once a minute. `reconnect.give_up_after_secs` and `reconnect.on_rejected: exit` exist for setups where a supervisor should notice; neither is written by `init`. A rejected client keeps retrying by default, so fixing the server config later brings it back without touching the client machine.

## D19. Default ports 7835-7840

2333 is rathole's default, and 8080, 8081 and 8443 are among the most used ports on any host. burrow uses its own block, none of which is in the services database: 7835 for TCP clients, 7836 for WebSocket behind a proxy (bound to 127.0.0.1), 7837 for WebSocket with its own TLS, 7839 for the local `burrow admin` UI, and 7840 for the example service written by `init`.

## D20. `burrow service` instead of shipped unit files

Hand-written unit files go stale, differ per OS, and leave the hard parts to the user: a service account, file permissions, secrets that `sudo` dropped, log rotation, and updates. `burrow service` does them the same way on every platform, much like `cloudflared service install` and `tailscaled install-system-daemon`.

- **Admin only, system services only.** A per-user service would stop at logout on Linux and macOS. One install path keeps it simple.
- **A dedicated account, created by burrow.** `burrow` (useradd `--system`), `_burrow` (dscl, hidden, id below 500), or a Windows virtual account, which Windows creates with the service. Running as root would give an attacker who gets through the pre-auth parsers the whole machine. The account and the copied binary are removed by the last `uninstall` that used them.
- **Copies, not references.** The config is copied to the service's own folder, `/etc/burrow/<name>/<role>.yaml` (`%ProgramData%\burrow\<name>\` on Windows), and the binary to `/usr/local/bin`, because a service must not depend on, or run code from, a folder a normal user can write. The binary is always copied, even from a root-owned folder, so a service never depends on where burrow was downloaded (a 0700 `/root` would make systemd fail with 203/EXEC for the service account) and always runs from one predictable path; there is no official package to defer to, and the unrelated Debian package named `burrow` rules out guessing a package path. When users other than root can write `/usr/local/bin` (Homebrew on Intel Macs), the service gets its own copy in a root-only folder instead. If that folder turns writable after the install, the service stays manageable (status, logs, stop, uninstall, list), but burrow no longer runs or replaces the binary there; `service status` and `update` name the reinstall that moves it to the root-only copy. Accepted risk: until that reinstall, a service installed with `--run-as root` still starts the binary in that folder as root, and `sudo burrow` in the hint runs whichever `burrow` is first on PATH; this is the same for every root daemon and every `sudo` use under a user-writable `/usr/local` (Homebrew).
- **Checks before changes.** The config is validated, every listen port is test-bound and its owner is named, and the instance lock is tried before anything is written. A failed reinstall restarts the previous service.
- **Own log files** with size-based rotation (10 MB, 5 files) rather than journald or the Windows event log, so `burrow service logs` works the same everywhere and a log cannot fill the disk. Startup failures are written there too, so a Windows service that has no console still says why it stopped.
- **Updates:** `burrow service update` replaces the binary only when it is newer, keeps the previous one, restarts every affected service and rolls back if one does not come up. `burrow update` downloads a release itself (D29).
- **Crates:** `windows-service` (Mullvad) for the Windows dispatcher and SCM; systemd and launchd are driven through `systemctl` and `launchctl`, which are their stable interfaces.

## D21. Ask only for what burrow cannot know, but write every field

`listen` says where the server binds on its own machine, usually `0.0.0.0`. Behind NAT, a cloud firewall or DNS it says nothing about how clients reach it, so the client address is never guessed from it. `client-config` takes it from `--server`, or from the optional `public_address` in the server config, so it is typed once for all clients, and otherwise stops with a hint. A host alone gets its port from `listen`, which is the one thing `listen` does tell. `0.0.0.0` is refused; loopback and private addresses are allowed with a note, because tests, LANs and VPNs need them. Notes only warn about something that may not work.

Config files accept short forms (`listen: 7835`, `target: 3000`, `server: host`), but required fields stay required, and `init` still writes `listen`, `bind`, `target` and `allow` in full, because a generated file is also the user's documentation. `init` writes `public_address` only when `--server` is given, because a placeholder would be an invalid value. WebSocket stays off unless its section is written.

## D22. Visitors: private by default, `reach` as an opt-in

Some services should not be public at all: a database, SSH, an admin page. frp (`stcp` with a visitor) and rathole leave this to a second tool or a firewall rule. burrow lets the server relay a visitor to a client without opening a port.

- **The server's config still decides.** A service without `bind` is private, and lists its `visitors`. A visitor reaches only those services, so a leaked visitor secret exposes what was listed and nothing else.
- **`reach: { CLIENT: any }` is the explicit opt-in** for `ssh -L`-style access, where the visitor picks the target. It is bounded by the client's `allow` list, which the client owner controls and which a compromised server cannot widen. `validate` warns about every `reach: any`, because `init client` writes a broad `allow: [127.0.0.0/8]`.
- **Visitors are not clients.** They have their own section, secrets and limits, they never expose anything, and their names are looked up only for visit channels, so a visitor secret cannot open a client session or the other way round. The same constant-work rejection hides which names exist.
- **One channel per local connection**, with the same handshake as data channels. A visitor keeps no long-lived connection, so it has nothing to reconnect, and the server keeps no state for an idle visitor. The cost is one handshake per connection plus one round trip, because the visitor waits for the server's answer before sending data so that a refusal always carries its reason. The server also decrypts and re-encrypts every record between the two channels: on one loopback machine a visit carries 7.8 Gbit/s on one stream and 22.7 Gbit/s on four, against 12.9 and 35.0 for a public service.
- **`local` defaults to `127.0.0.1`,** unlike `bind` on the server: anyone who can reach a forward uses the visitor's access, so sharing it with a network has to be written out, and `validate` warns about `0.0.0.0`.
- **Reload revokes**: open visits re-check their request when the config changes, as a removed client's connections do.
- **TCP and UDP** since v0.1.2: see D42.

## D23. Port ranges are one service

A range like `bind: 30000-30010` stays one service with a first port and a count, instead of eleven generated services. `max_connections`, `bandwidth`, metrics and logs then describe what the user wrote. Each public port has its own listener and maps to the same position in the target range; a visit request carries the index. A range holds at most 1000 ports, so a typo cannot open tens of thousands of sockets.

## D24. PROXY protocol written by the server

The server knows the real source address, so it writes the PROXY v1 or v2 header into the tunnel right after Connect, and the client forwards it as data. Clients need no change, the same code covers visits (with the visitor's address), and the header works in `insecure_plaintext` mode too. It is off by default and per service, because a target that does not expect it fails on the first bytes. Checked against nginx `listen ... proxy_protocol` with both versions.

## D25. Several clients, and health checks through the tunnel

A service can list several clients. `failover` takes the first connected one, `balance` rotates new connections; an open connection never moves. Health checks run on the server and use the tunnel itself: a normal Connect to the target through each client, closed at once. This needs no client config, tests the real path including the client's allow list, and works with any target the client can reach. A client is down after `failures` failed checks in a row and up again after one success. When no client passes, connections still go to a connected one, so a broken check cannot take a working service down.

Without health checks, the server still learns from real connections. While it waits for the client's answer it keeps a copy of what the visitor sent (up to 64 KiB, then it stops reading until the answer), so when a client answers that it cannot connect, cannot resolve the target or refuses it, the same connection goes to the next client and the visitor notices nothing. A client that does not answer in time counts as failing too, but its connection moves on only if the visitor has sent nothing yet: the client may still deliver those bytes, and a request must never reach the target twice. A channel that breaks says something about the session, not the target, and counts for nothing; a client that cannot hand over a data channel in time is set aside like one that does not answer, for TCP as for UDP. A refusal comes from the client's config, which only changes when it reconnects, so that client is skipped for the target until then; a target it could not reach is skipped for 10 s, doubling up to 60 s while it keeps failing, and the first success clears it. Skipped clients stay at the end of the list and are still tried when all others fail. A service with one client keeps no copy and works as before. This is what nginx does by default (`proxy_next_upstream`, `max_fails`), and it avoids probing every target through every client every few seconds, which shows up in the target's logs.

## D26. Bandwidth limits

One token bucket per service and direction, shared by all its connections and ports, refilled continuously with a burst of 100 ms (at least 16 KiB). TCP waits for tokens, so senders slow down through normal backpressure; UDP has no backpressure, so datagrams over the rate are dropped, as a router would. Throughput, latency and connection rate without a limit are unchanged (measured against the previous commit).

## D27. Metrics off by default, one snapshot for everything

The metrics endpoint is off unless `metrics.listen` is set, defaults to `127.0.0.1`, and `validate` warns when it is reachable from the network, because it shows client, service and visitor names and traffic. The server builds one status snapshot; `/metrics` renders it as Prometheus text and `burrow status` reads it as JSON from a local endpoint only it can use, so the two can never disagree. The metrics port serves nothing else: the JSON holds more than a scraper needs, such as client addresses. Counters are relaxed atomics updated per read, with no measurable cost.

## D28. A SOCKS5 forward for visitors

`reach` lets a visitor pick any target its client allows, but one forward per target is tedious. A SOCKS5 forward (`socks: true`, or `visit --socks`) reads the target from each SOCKS request and sends it as a normal reach request, so the server and the client's allow list decide exactly as before. CONNECT and, since v0.1.2, UDP ASSOCIATE are supported, without authentication: the listener is on `127.0.0.1` by default, like any forward. See D42 for UDP.

## D29. Our own updater instead of a crate

`burrow update` downloads a release with the TLS, proxy and HTTP pieces burrow already has, checks it against `SHA256SUMS`, runs it to confirm its version, and hands it to `service update` for rollback. The `self_update` crate would have added 2.3 MB (42%) and about 100 crates to the binary and ignored burrow's proxy settings; the own code adds about 110 KB and one small dependency for gzip.

## D30. WebSocket channels end with TLS close_notify

A data channel over `wss://` used to end by dropping the connection. A TLS proxy in front of the server can treat that as an error and drop the last message of the stream under load, which a test reproduced (80 KB missing out of 8 MB). Channels now shut down the TLS layer below the WebSocket, which sends close_notify and a FIN. A WebSocket Close frame as well would cost 3-5% of new connections per second for no benefit, because the record layer already marks the end of each stream.

## D31. Clients and visitors reload on save, like the server

Everything that changes often lives in the server config, so clients were first left to apply changes on restart. That cut every open connection for what is usually an `allow` edit. Clients and visitors now watch their file (and take `SIGHUP`) through the same reload loop as the server: the new file is checked like `validate`, and a file that does not load is rejected while the running config stays. A client compares field by field: `allow`, `server`, `name`, `secret`, `headers`, `ca`, `cipher`, `proxy` and `insecure_plaintext` make it reconnect, the rest applies to the next connection. `allow` reconnects because the server skips a client that refused a target until that client reconnects (D25); a protocol message could avoid that, at the cost of a wire change right before a release, and the reconnect costs about a second. Connections that are being set up at that very moment fail (measured: a few dozen at 64 parallel connection attempts), since the data channels of the old session close with it. Open connections run on their own data channels and survive the reconnect, except those whose target the new `allow` no longer permits, which are closed as on the server. A new `server` or `name` first takes the instance lock of the new identity, so a reload cannot make two clients run the same tunnel. A visitor has no session: connection fields apply to new connections, and only the forwards that changed are closed or opened.

## D32. A visitor asks the server for its own config

`burrow visitor-config` needs the server config, so a visitor depended on the server's admin for every change. The visit channel now answers one more request, "what may I use?", after the same handshake and secret check as a visit, with the same grants that `visitor-config` writes (one function decides both, so they cannot differ). `burrow init visitor` uses it for a new file, and `--update` merges it into an existing one: forwards you have keep their local ports and names, new grants get free ports, revoked ones are removed, the changes are shown before anything is written, and only the `forwards` block of a YAML file is replaced, so other lines and comments stay. To say what `reach` means, a client sends its `allow` list once per session; the server shows it only to visitors with `reach` for that client, who may already use any target it permits.

## D33. Admin over the visit channel, never a new port

`burrow admin` edits a running server's config from a browser on the admin's machine. The server exposes nothing new: an admin channel is a visit channel with the visitor's secret and a different first request (protocol section 11), so it gets the same anti-enumeration handshake, deadline and limits, and a visitor without rights gets the same `5 forbidden` as any refused visit. Rights are opt-in per visitor in the server config, `admin: read | write`, optionally limited to source addresses with `admin_from`. Only these two levels exist; finer rights can be added later as a new field. A write admin without `admin_from` gets no warning, because that is the simple setup most people run. `validate` warns when an admin visitor also uses services or `reach`, since one leaked secret should not give both. On every reload the session checks its visitor again and ends when the right, the secret or the source is gone, or the level changed. An installed server can write its own config only when it has an admin visitor (or `service install --admin-writable`): then the service account owns the service's config folder and the sandbox lets it write there, and otherwise root owns the folder, the sandbox stays as tight as before and the UI says honestly that it is read-only, with the exact command that changes it. Every service has that one folder from its first install, so switching admin writes on or off only changes the folder's owner and nothing moves; installing again from the installed config itself (`-c /etc/burrow/<name>/server.yaml`) is allowed and reinstalls that service, because the downloaded source may be gone and the installed copy is the truth. The env file with secrets stays outside the folder (`/etc/burrow/<name>.env`), so a writable folder never holds it. Before each admin write the previous file is kept beside it (`.server.yaml.history/`, the last 20, mode 0600), so a change can be reverted; when that folder cannot be written the history is kept in memory only.

## D34. Schema-driven admin UI with semantic types; completeness by derive

The server describes its config to the UI as a schema of semantic types (`ip_port`, `target`, `cidr_rule`, `ref<client>`, `ref_list<visitor>`, `duration`, `rate`, `secret_ref`, ...) with relations such as "only for TCP services" or "one of client and clients". It never names a widget; the UI decides that a `ref_list<client>` is a multi-select of the clients with their online state. Core screens are laid out by hand and place fields by key, and every field they do not place, including fields a newer server adds, is rendered by a generic renderer from the same types. Types a UI does not know come with a `fallback` chain ending in a text input that the server validates, so an older UI keeps working against a newer server and never shows a broken field. The schema comes from the config model through `#[derive(AdminSchema)]`: every field and every enum variant must carry `#[admin(...)]` or `#[admin(skip = "reason")]`, otherwise the build fails on that field, and the macro checks that the semantic type fits the Rust type. Descriptions and ranges are read from the existing `schemars` and `serde` attributes, so they are written once. The model lives in the crate `burrow-config`, shared by the server and the UI, and the derive also emits a typed path for every field (`ServiceEntry::BIND.of("web")`), so the UI and the server's admin code never name a config field by string, `cargo xtask arch-check` refuses such a string, and a renamed field fails to compile at every use. The UI still renders from the schema the server sends: the typed paths only name fields, and a field the live schema lacks is left out. Server-delivered UI code was rejected: the browser runs only the UI embedded in the local binary.

## D35. Comment-preserving patcher with verification

An admin change is a list of operations on paths, never text. The server applies them to the raw tree of the file and turns the difference into byte edits on the spans of the existing parser: a changed value replaces its span, a new key is inserted after its siblings with their indentation, a removed key takes its leading comment block with it, and the BOM, line endings and every other byte stay. Each result is parsed again and must give exactly the wanted tree; otherwise nothing is written. The result is then checked by the same function as `validate` and reload, the plan with its diff is shown, and the write uses the same atomic, revision-checked save as `burrow edit`. Accepted risk: on Windows that save writes the file in place, so its ACL and owner stay; it first writes a spare copy beside it, and when the config then fails to parse, the error names the spare to restore from. An atomic `ReplaceFileW` would need unsafe code, which waits for the owner's decision. JSON files have no comments and are re-rendered in key order with their indentation. A second YAML library (`yaml-edit`) was considered and rejected: two parsers could disagree on files that `validate` accepts, and it adds 150-250 KB.

## D36. Local UI security: loopback, fragment token, no cookies, Host/Origin checks

`burrow admin` listens on `127.0.0.1:7839`, or on a free port with a note when 7839 is taken (`--port N` is strict, `--port 0` always picks a free one), and never on another address. Each session serves its pages, routes and `/api` under a random 128-bit path prefix (`/r-<hex>/`), made new when a session starts and kept with it for up to 12 hours (D40), so a process that held the port earlier cannot have its poisoned cache entries match this run's URLs, and `/api` is reachable only under the prefix, never from a cached page at a fixed path. Every file is served `Cache-Control: no-store` and the pages add `Clear-Site-Data: "cache"`; remote use goes through `ssh -L`. A 256-bit token is required as the first WebSocket message; it reaches the browser in the URL fragment of a 0600 launch file in the private instance folder, so it is never on a command line, in a request or a Referer, and the page removes it from the address bar. There are no cookies, which are not isolated by port, and no CORS headers. Every request must name the local host and port in `Host` (against DNS rebinding), the WebSocket upgrade must come from exactly that `Origin`, and a request whose `Sec-Fetch-Site` is not `same-origin` or `none` is served only as a top-level navigation (`Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`, as when the browser arrives from the launch file or a link), never as a script, style, fetch or `/api` request; a navigation straight to an asset URL is served too, but asset URLs exist only under the session's 128-bit prefix, which another site cannot know; framing is denied, and `/api` always needs the exact `Origin` and the token. Pages carry a strict CSP without inline scripts, and server-provided text is only ever inserted as text. The bridge in `burrow admin` passes admin messages through without reading them, so it does not have to change when the protocol grows. Accepted risk: with a fixed default port, a hostile local user who once served the browser on 7839 and kept that connection open can answer the first request of a later run; burrow accepts this, as tools with a fixed local port and a token do (Jupyter on 8888).

## D37. Leptos CSR, own design system, built once and embedded

The UI is Rust compiled to WebAssembly with Leptos in client-side rendering mode, so it shares the value parsers with the server and the product stays one language. Leptos has fine-grained signals, which suit large live forms and once-a-second status, and it is the most used and documented Rust web framework; Yew and Dioxus are larger or slower to update, Sycamore has few users. The component kit is our own small set of controls with plain CSS and design tokens: the main Leptos kit is pinned to an older Leptos and its look would have to be fought. CI builds the WebAssembly once, compresses it and embeds the same bytes into every release target, with a size budget; a plain `cargo build` without the wasm toolchain embeds a placeholder page instead.

## D38. `self`: the server as its own client, behind two gates

A server often runs next to things worth exposing (a database, a web app, its own LAN), and needing a client process on the same machine for them was pointless. `self` is one reserved name: the client of a service, a key of `reach`, and a config section, and a real client named `self` is refused. It is implemented as a client that runs inside the server: a connection for `self` gets an in-memory channel whose other end is served by the same target code as a remote client (DNS, allow check after resolving, reach rules, Unix sockets, UDP peers, closing what a reload no longer permits). Routing, failover, health checks, limits, the PROXY header and the relay do not know the difference, because they see a channel like any other. The channel carries the usual records unencrypted (a zero tag, same framing, so an end of stream still differs from an abort); only the in-memory pair can be built that way, so no network transport and no config flag can reach it.

- **Two gates.** A visitor's `reach: self` rules are checked first, then `self.allow`, so the effective set is their intersection, as `reach` and a client's `allow` list are for remote clients. Without `self.allow`, `self` services reach their own target and `reach: self` is a validate error. `self.allow` covering a whole address family is warned about, like `allow_all` on a client.
- **What the server never dials for itself:** its own listen, WebSocket and metrics addresses over TCP (any address of this host on such a port when it listens on all of them), and link-local or cloud metadata addresses (169.254.0.0/16, fe80::/10, the AWS IPv6 endpoint fd00:ec2::254 and Alibaba's 100.100.100.200) unless `self.allow` names the address on its own; a range covering them does not count. One function decides this for `validate`, the admin UI and the data path. Another machine's address on that port stays allowed, and so does a NAT-hairpin public IP that no interface carries, as it would be for a remote client, since that listener is public anyway.
- **Status:** `self` is listed as a client marked `local`, always connected, whenever the config uses it; remote clients keep their exact JSON.
- **Cost, measured on loopback** (iperf3 and loadgen): 22 Gbit/s on one stream, 71 Gbit/s on four, 16-18k new connections per second, against 13 and 36 Gbit/s and 14k for a remote client on the same machine, which was unchanged by the seam.

## D39. burrow admin reduces admin power but never grants it

A stolen admin secret or browser session must not be able to make itself permanent, so nothing that decides who may administer can be widened through burrow admin: a new admin, `read` to `write`, a new secret on an admin visitor, a wider `admin_from` (checked against the union of the old ranges, an empty list meaning everywhere) and a renamed admin visitor are refused on every plan path, revert included, and need a file edit (`burrow edit`, an editor or ssh). The base is the current file, not the running config, since only someone with file access can put a grant there; when the file fails its checks, a grant is refused if it widens either the running config or the file's raw tree, so a broken file cannot open a way around the check. Reducing stays possible from the UI, so a leaked admin can still be revoked from there. The fields are marked `reduce_only` in the schema, so the UI offers them only towards less power through the same decision the server uses. Limit: a write admin can still change services, `reach` and everything else, so this keeps the attacker from staying, not from acting.

## D40. burrow admin keeps its session for 12 hours

A browser tab used to outlive its `burrow admin`: the next run made a new token and path prefix, so the old tab retried forever and a new tab opened each time. Now the token, the path prefix and the port of a run are kept in a 0600 file in the user's own state folder (`~/.local/state/burrow/admin-sessions` on Linux, the local app data folder elsewhere), one per visitor config, the same model as Jupyter's runtime file. The next `burrow admin` for that config reuses them while the file was used in the last 12 hours, so an open tab reconnects by itself, and expired session files are deleted the next time burrow admin starts; when an open tab reconnects within 3 seconds of the start, no new tab is opened and the terminal says so. A tab that reaches a `burrow admin` which refuses its token or no longer serves its prefix stops retrying and says that its session ended; while nothing listens it says that `burrow admin` is not running and retries every 2 seconds. Accepted risk: the token is at rest in a file only the user can read, and an open tab sends it to whatever listens on that local port while `burrow admin` is stopped, so a hostile local user who takes the port in between can learn it and use it until the session expires; this is the risk Jupyter accepts for its token file and fixed port, and D36 already accepts a hostile local user on the port.

## D41. macOS builds signed with burrow's own certificate

With the macOS application firewall on, a program that listens is allowed or blocked by its code signature. An unsigned build only has an ad-hoc signature tied to its exact bytes, so every `burrow update` looked like a new program: the firewall asked again, and on a Mac with nobody logged in it blocked the updated service silently and kept it blocked (measured on macOS 14). Release builds are therefore signed in CI with one self-signed code-signing certificate (`scripts/macos-signing-cert.sh`, repository secrets `MACOS_CERTIFICATE` and `MACOS_CERTIFICATE_PASSWORD`) and the fixed identifier `com.github.charlesng35.burrow`; the firewall then asks once per install path and keeps the answer across updates. A tagged release fails rather than publish an unsigned macOS build. The certificate must never be replaced, or every Mac asks again. It does not make Gatekeeper trust a browser download; that needs a paid Apple Developer ID and notarization, which can be added later without changing this identity's role.

## D42. UDP for visitors, and SOCKS5 UDP ASSOCIATE

A visitor reaches private UDP services and UDP targets in `reach`, with the same server-side checks as TCP. The client is unchanged, so v0.1.0 and v0.1.1 clients serve UDP visits.

- **The data path:**
  - A UDP forward has one socket per local port. Its first datagram opens one visit channel (VisitRequest flag bit 1, protocol.md section 9). The channel carries the records of a UDP service (`peer:u32 || datagram`), with peer ids chosen by the visitor and passed on unchanged.
  - The server admits at most `udp.max_peers` peer ids per visit, takes the service's bandwidth (D26) for a visitor's datagram only once it is admitted and for every reply, as on the public UDP relay, drops what is over the rate, and follows a service's clients with the same failover as TCP (D25).
  - The visitor closes the channel once its peers have expired, and the server closes a visit with no datagram either way for `udp.session_timeout_secs`. An idle visitor keeps no server state (D22).
  - A reload closes a visit that is no longer granted, and a UDP service visit whose target changed. TCP connections keep running in that case; the next datagram opens a new UDP visit to the new target.
  - The socket-to-channel loop is shared with public UDP services (`src/udp/front.rs`).
- **Protocol is explicit.** A forward has `protocol: tcp|udp`, like a service, and is never inferred. The visitor binds before it talks to the server, and a wrong guess would bind the wrong socket. A mismatch is answered `4 invalid`, and `burrow visit` asks for the grants to say which protocol to set. A server older than v0.1.2 answers `4 invalid` to the UDP flag and to `0x21 0x01` (checked against v0.1.1). `init visitor` then falls back to TCP-only grants and keeps existing UDP forwards. A v0.1.2 server whose grants do not fit in one answer gives the same `4 invalid`, so the message names both causes.
- **`reach` stays address-only and covers TCP and UDP**, like a client's `allow` list and a service's `allow_from`. A `reach` grant gives the same addresses and ports over both protocols, so an existing grant now also allows UDP to them; the client's `allow` list still has the final say. A per-protocol rule or an opt-in flag would add config for little gain: `reach: any` already gives arbitrary TCP. `validate` says "over TCP or UDP" in its `reach: any` warning.
- **`self`** follows D38 for UDP through the same gate: the server's own TCP listen, WebSocket and metrics ports stay TCP-only refusals, and link-local and metadata addresses need `self.allow` to name them. A `unix:` target is refused for UDP (`4 invalid`) before any client sees it.
- **Limits and timers:**
  - `udp.session_timeout_secs` now defaults to 120 s on the server, client and visitor (was 60 s). RFC 4787 section 4.3, REQ-5, says a NAT UDP mapping "MUST NOT expire in less than two minutes", except for some well-known ports, and recommends five minutes or more (REQ-5c). RFC 4787 is updated by RFC 6888 and RFC 7857, and neither changes REQ-5. The cost is that peers that change source port per request, such as DNS, are held longer: at the default `max_udp_peers` 8192, a client drops new peers above about 68 such queries per second, instead of 136. The value stays configurable.
  - Mappings are refreshed by outbound traffic, which REQ-6 requires.
  - Following RFC 8085, datagrams are never fragmented or queued without bound. The largest datagram is 65515 bytes and larger ones are dropped with a debug line. Over-rate datagrams are dropped, not delayed. Every queue is bounded: per channel, per SOCKS destination, and 1 MiB per SOCKS association.
  - A UDP visit counts as one connection of the visitor and of the client. The service's `max_connections` stays TCP-only.
- **Spoofed sources:** a UDP forward or SOCKS relay listening off loopback accepts any source address, as UDP has no handshake, so a forged one can fill `udp.max_peers` and send replies elsewhere. docs/visitors.md says to keep `local` on 127.0.0.1 unless the network is trusted. Popular tools accept the same risk for UDP listeners.
- **SOCKS5 UDP ASSOCIATE** follows RFC 1928:
  - §4 and §6: the relay port is bound on the address the app connected to, made plain IPv4 when the forward listens on a dual-stack `[::]`. The reply gives that relay address in BND.ADDR and BND.PORT. A v4-mapped address cannot be used by an IPv4 app, and fails where IPv6 sockets are IPv6-only by default: Windows sets IPV6_V6ONLY by default (Microsoft Learn, "Dual-Stack Sockets"), and FreeBSD has `net.inet6.ip6.v6only` on by default (inet6(4)).
  - §7: datagrams from any source other than the app are dropped. The relay admits the IP address of the app's TCP connection only, and an address named in the request on another host is ignored, so the relay cannot be aimed at a third party. A port named in the request must match; otherwise the first sender's port is locked in.
  - §7: fragmentation is optional, and an implementation without it MUST drop FRAG not 0, so it is dropped with a debug line.
  - Replies carry the header the app sent, so a host name stays a host name; the client resolves names (D28).
  - Each destination gets its own visit (kind 2), so the client stays unchanged and `reach` and `allow` decide per destination. There are at most 64 destinations and 1 MiB of waiting datagrams per association.
  - The association ends when its TCP connection closes (§6), and also after `udp.session_timeout_secs` with no datagram.
  - Header parsing is strict (reserved bytes 0, ATYP 1, 3 or 4, exact lengths, a valid host:port, port not 0) and has its own fuzz target, `socks_udp_header`.
- **No SOCKS crate:**
  - `socks5-proto` (0.4.1) and `socks5-impl` (0.10.3) are GPL-3.0-or-later, which our MIT licence and deny.toml exclude.
  - `socksv5` (0.3.1) has had no release since 2022-12-08.
  - `fast-socks5` (1.0.0, MIT, maintained) would replace only about 40 lines of UDP header parsing. It would also add a second socket2 (0.5) and a typestate server that does not fit our refusal handling.
  - So burrow keeps its own strict, fuzzed parser, as it did for CONNECT. This should be revisited if fast-socks5 offers standalone parsers that do not need its server.
  - Sources: crates.io and docs.rs pages of each crate, checked 2026-10-23.

## D43. Websites on one HTTPS port: the web: block, one crate, one seam, nothing hidden

burrow can put several TLS services and, later, websites on one HTTPS port of the server, told apart by name, and the WebSocket tunnel can share that port (docs/web.md). The shape:

- **Off unless written.** Nothing listens unless the top-level `web:` names `https`. A service becomes a website by having its own `web:`; a service `web:` without the top-level block, or in a build without the `web` Cargo feature, is a validate error, so a key never does nothing. The tunnel shares the port only when `websocket.listen` is written the same way as `web.https` (both a bare port, or the same ip:port; a mix is an error) and `websocket.host` names it. `burrow validate` (text and `--json`), `burrow status` and the admin overview show the same summary, built by one function from the settings.
- **One word, `web`.** The config key, the Cargo feature, `src/server/web.rs` and the crate `burrow-web` use it. The service block (`web: name`, `web: [a, b]` or `{hosts, tls}`) keeps the tunnel part of the service unchanged: clients, `self`, failover, health checks, `allow_from`, `max_connections`, `bandwidth` and `proxy_protocol` work for websites as for a TCP service, because a website connection is a normal service visit.
- **The crate.** `crates/burrow-web` holds the listener, the TLS name peek, the PROXY header reader, the name table, the pre-TLS limits and the tunnel hand-off. It never depends on `burrow`, `burrow-config` or the admin and UI crates, and they never depend on it (`cargo xtask arch-check`), so the WebAssembly UI does not grow.
- **The seam.** `Upstream::open(service, &Visitor { addr, local, host })` returns one boxed stream (`Box<dyn Io>`). It differs from the design sketch in three ways: it carries the local address, so the PROXY header to the app names the real HTTPS port; it hands the tunnel over with `tunnel_permit(peer)` and `tunnel(TunnelConn)`, so a tunnel connection moves from the web pool of pre-TLS slots to the tunnel's own `max_handshakes` pool before TLS starts and the two pools cannot starve each other; and `open` refuses up front only what is known before a client answers (`allow_from`, `max_connections`, no client). The root crate implements it with an in-memory pipe and the existing `visit()`, now generic over `Split`. A pipe end carries a reset flag, because a dropped tokio `DuplexStream` reads as a clean end of stream (tokio docs, `DuplexStream`), and a target that resets must reach the browser as a reset.
- **Reading the name.** The first TLS message is read with rustls' `Acceptor` fed with copies of the bytes, and the bytes are then replayed to the app or to the TLS acceptor. Limits: 10 seconds, 16 KiB plus a record header, the first byte must be a TLS handshake record (0x16), a hello split over several records is read whole, and any Acceptor error closes the connection without an answer. The name is compared without case and without a final dot (RFC 6066 section 3, which also forbids IP literals in the name). A connection without a name reaches the site of the address it connected to, if one lists it. An unknown name is closed without a certificate. A wildcard covers exactly one label (RFC 6125 section 6.4.3, now RFC 9525 section 6.3).
- **PROXY headers from a load balancer** are parsed by `ppp`. A v1 line has at most 107 bytes (HAProxy specification). The reader takes at most 536 bytes: the specification designs both versions to fit in one minimal TCP segment of 536 bytes, but v2 itself is 16 bytes plus a 16-bit length, and its TLVs have no total limit, so 536 is burrow's choice for now and the final cap is decided with P3. LOCAL and UNKNOWN keep the real peer; bytes after the header are kept. The reader and its fuzz target exist now; `web.proxy_protocol_from` turns it on with the rest of P3.
- **The tunnel by path.** On a name that a site shares with the tunnel, burrow answers the WebSocket upgrade on the tunnel's path itself and hands the upgraded stream to the same WebSocket code (`ws::serve_upgraded`), with the same message, control-frame and keepalive limits. tokio-websockets 0.13.3 keeps its request parser private (`upgrade::client_request` is `pub(crate)`), so the accept key is computed in one small function with ring's SHA-1 and base64 as RFC 6455 section 4.2.2 says, tested with section 1.3's example; another version than 13 gets 426 with `Sec-WebSocket-Version: 13`. One `limits.handshake_timeout_secs` covers TLS, the upgrade and burrow's handshake together.
- **Dual stack.** A bare `web.https` port binds `[::]` with `IPV6_V6ONLY` cleared explicitly, through the same `bind_tcp` as every listener, because the default differs: Linux follows `net.ipv6.bindv6only` (0 by default), Windows sockets are IPv6-only by default (Microsoft Learn, "Dual-Stack Sockets"), and FreeBSD has `net.inet6.ip6.v6only` on by default (inet6(4)).
- **Final forms first.** A site's `tls` is `auto` (the default with `web.https`), `passthrough`, `off` or `{cert, key}`, and `web.https` is optional in the model (`web:` needs a port). Until termination exists, validate accepts only `passthrough` and refuses each other form with a message that names the fix, so later phases lift rules instead of changing the config. The tunnel's name takes its certificate from `websocket.tls`.
- **What the admin UI may change.** The web proxy itself is editable in `burrow admin`, except what opens ports or reads files: `web.https`, `web.http`, `web.letsencrypt.ca`, the `cert` and `key` of each `web.certificates` entry and of a site's own `tls: {cert, key}` (config.md section 6). A lock can now name entries of a map or list with a `*` segment (`services.*.web.tls.cert`), and a plan from the admin channel is refused when it would set or change any locked value, whatever path the change takes (a field, its parent, the whole service, raw text, a new service); removing an entry that holds one is allowed, and a revert keeps the current locked values. Top-level locked values may not be removed either, so turning the web proxy off stays in the file.

Sources, checked 2026-10-24: RFC 6066 section 3; RFC 6125 section 6.4.3 and RFC 9525; RFC 6455 sections 1.3 and 4.2.2; the HAProxy PROXY protocol specification (proxy-protocol.txt, versions 1 and 2); rustls `server::Acceptor` docs (0.23); tokio `io::DuplexStream` docs; man7.org `IPV6_V6ONLY(2const)`; Microsoft Learn "Dual-Stack Sockets for IPv6 Winsock Applications"; FreeBSD inet6(4); the Cargo book, "Workspaces" (a bare `cargo test` in a workspace with a root package tests only that package, so CI names `-p burrow-web`); tokio-websockets 0.13.3 source, `src/upgrade/mod.rs`.

## D44. HTTPS termination: one peek, one shared config, Host equals the TLS name

burrow ends TLS itself for a site whose `tls` is `auto` or `{cert, key}` and speaks HTTP/1.1 to the browser with hyper, then sends each request to the site's service through the same `Upstream::open` seam as passthrough (D43). The shape:

- **The peek decides.** Every connection on `web.https` is read up to the end of its TLS hello first (D43). The name picks one of four ways: passthrough replays the hello to the app; the tunnel's own name hands the stream to the tunnel; a name whose site only holds the tunnel by path goes to the tunnel's HTTP code; a terminated or plain site gets burrow's TLS. The bytes already read are replayed into rustls through `Prefixed`, so the peek costs no second read and the hello is parsed by rustls itself, not by burrow.
- **One shared server config.** All terminated names share one `ServerConfig` built once with `with_cert_resolver(Certificates)`, so a new or renewed certificate is used by the next handshake without rebuilding anything, and open connections keep the session they have (a test swaps a site's file on reload and keeps an open connection working). ALPN offers only `http/1.1`: a hello that offers protocols and none of them overlaps is refused by rustls with `no_application_protocol`, as RFC 7301 section 3.2 says, and a hello without ALPN proceeds. HTTP/2 is not offered yet. The provider is ring with rustls' safe default versions (TLS 1.2 and 1.3).
- **Per-connection configs only where needed.** A hello without a name that reaches an IP site (RFC 6066 section 3 forbids IP literals in SNI, so browsers send none) gets a config holding that site's one certificate, because the resolver is keyed by name. A hello that offers exactly `[acme-tls/1]` for a name with a pending TLS-ALPN-01 challenge gets a one-shot config with the challenge certificate and ALPN `acme-tls/1` only; after the handshake burrow closes the connection, since the protocol carries no application data (RFC 8737 sections 3 and 4). `acme-tls/1` is never in the shared config, so a visitor can never negotiate it, and a hello that offers it beside `http/1.1` gets `http/1.1`. A passthrough name without a challenge gets its hello to its app unchanged, `acme-tls/1` included.
- **Host must equal the TLS name.** The request's host is the one `Host` field, or the authority of an absolute-form target, which wins (RFC 9112 section 3.2.2), lowercased, without port or final dot, an IPv4-mapped IPv6 address in its IPv4 form. A request without a Host, with two, or with one that is not a valid authority (userinfo included) gets 400 (RFC 9112 section 3.2). On a TLS connection a host other than the name of the hello gets 421 Misdirected Request (RFC 9110 sections 7.4 and 15.5.20), because the certificate only proves that name and RFC 6066 section 11.1 makes a server that relies on the names being equal check it. This also stops a browser's connection reuse from carrying a request to another site. CONNECT gets 400.
- **Every limit explicit.** hyper's http1 server runs with `header_read_timeout` = `web.request_header_timeout_secs` (10 s; since hyper 1.6 the same timer also runs while a kept-alive connection waits for its next request, hyperium/hyper#3828), `max_header_size` 32 KiB and `max_headers` 100 (both answer 431 and close), `keep_alive` on and `half_close` off. hyper itself refuses the smuggling shapes: Content-Length with Transfer-Encoding is read as chunked with the length dropped, two different lengths and an unknown transfer coding are 400 and close, and an obs-fold is 400 (RFC 9112 sections 5.2, 6.3 and 11.2); tests send each one and check that nothing hidden in a body reaches the app.
- **The idle rule.** A connection is closed when for `web.idle_timeout_secs` (60 s) no byte has moved either way and no request is in flight. A wrapper around the stream stamps the last byte and the service counts requests in flight, with one timer per connection. A slow app that is still working on an answer is never cut by it (`response_header` covers that, 504 after 60 s), and an upgraded connection such as a WebSocket is never idle-closed: once joined, it belongs to the two ends.
- **The upstream.** One hyper client stream per browser connection and service, opened through `Upstream::open` and reused for the next request when it is ready within a second. Hop-by-hop fields are removed both ways: those named in Connection, and Connection, Keep-Alive, Proxy-Connection, TE, Trailer, Transfer-Encoding and Upgrade (RFC 9110 section 7.6.1). X-Forwarded-For and X-Real-IP are set to the visitor's address, replacing what the browser sent (trusted proxies come later), with X-Forwarded-Proto, X-Forwarded-Host and X-Forwarded-Port. Host passes unchanged; an absolute-form target becomes origin-form with Host set to its authority. A 101 from the app joins the two upgraded streams.
- **Pages before the first byte, resets after.** A refusal known before the app answers is a short built-in page on a connection that stays usable: no client or a client down 503, a client at its limit 503 with `Retry-After: 10`, not allowed 403, a denied or unreachable target 502, an app that resets before answering 502, no answer in time 504. Once the app's answer has started, a failure resets the browser's connection, as passthrough, the tunnel and plain TCP services do, so a cut-off body is never mistaken for a whole one. Pages exist for 400, 403, 404, 413, 421, 429, 502, 503, 504, the certificate-pending 503 and maintenance.
- **The drain.** On stop or when the web proxy is turned off, each connection gets hyper's `graceful_shutdown`: a request in flight finishes and is answered with `Connection: close`, idle kept-alive connections close at once, and after 10 seconds whatever is left is dropped.
- **Port 80 (`web.http`).** Plain HTTP goes through the same pipeline, without the 421 rule (there is no TLS name). In order: `/.well-known/acme-challenge/<token>` with a base64url token is answered from the ACME manager as `application/octet-stream` before any routing (RFC 8555 section 8.3); then the tunnel, when it shares this port (below); a `tls: off` site and an HTTPS site with `https_redirect: false` reach their app with `X-Forwarded-Proto: http`; other HTTPS sites get 308 Permanent Redirect to the same path on `https://` (RFC 9110 section 15.4.9 keeps the method and body), naming the port when it is not 443, or the pending page while their certificate is pending or failing, so a browser is never sent to a certificate error; passthrough, tunnel-only and unknown names get 404.
- **`web.https` optional.** Without it nothing listens on an HTTPS port and every site must be `tls: off` (decision 0b); a single-label name such as `nas` is allowed only on such sites (decision 0f).
- **The tunnel by path.** When `websocket.host` is a terminated site's name, the tunnel takes its path on that site's connections with the site's certificate from the shared resolver; validate refuses it on passthrough sites, on `tls: off` sites when it shares the HTTPS port, and on the path `/`.
- **The tunnel on port 80 (decision 0h).** When validate finds `websocket.listen` equal to `web.http` (`shares: Http`), the root sets `TunnelSettings.port` to `Http` and the tunnel rides that port over plain `ws://`, still encrypted end to end by burrow's own Noise layer. Each request on :80 is checked in order: the ACME HTTP check, then the tunnel, then `https_redirect` and the sites, so a redirect never catches the tunnel. On its own name the tunnel owns the whole name as on 443 (the WebSocket upgrade on its path is handed over, a plain request on the path gets 426, any other path 404); on a site's name, HTTPS or `tls: off`, it takes its path and below and the site keeps the rest. The upgrade goes through the same `tunnel::answer` and hand-off as the tunnel by path on 443 (RFC 6455 section 4.2.2). The tunnel then rides only that port: its name is closed on the HTTPS port, and it asks for no certificate.
- **Any port.** Sharing depends on `websocket.listen` being the same address as `web.https` or `web.http`, never on the number 443 or 80: the runtime has no port number in its rules other than leaving `:443` out of a redirect's address. The tests run on random high ports.
- **No sites.** A `web:` block without sites runs: on HTTPS every name other than the tunnel's is closed before TLS, on port 80 it gets 404, and the tunnel's own name gets its certificate through the shared resolver like a site (`websocket.tls`, a shared file, then Let's Encrypt). Which certificate a name gets, and which checks and wildcards are allowed, is config.md section 3.15's one set of rules (D45); termination only asks the resolver.

## D45. Certificates: own files, then Let's Encrypt, kept in a state folder of their own

burrow terminates HTTPS with a certificate per name, chosen in one order (config.md 3.9): the site's own `tls: {cert, key}`, then a `web.certificates` entry whose `hosts` lists the name, then `web.letsencrypt`, else validate refuses the name. A listed wildcard covers one label (RFC 9525 section 6.3); validate and the server pick the entry with the same function, `burrow_syntax::web::entry_for`, so they cannot drift. The tunnel's own name takes `websocket.tls` first.

- **Files.** PEM is read with rustls-pki-types `PemObject` (rustls-pemfile is unmaintained, RUSTSEC-2025-0134). The key is checked against the leaf with `CertifiedKey::from_der` and then `keys_match()` explicitly, because `from_der` accepts an unknown key match. A file must cover each name it is used for, checked by rustls-webpki (`verify_is_valid_for_subject_name`, the browsers' rules; a listed wildcard must be in the file as that wildcard). Dates come from x509-cert with its `Raw` profile, so a file rustls accepts is never refused for its dates; a warning comes 14 days before expiry. Files are read on a blocking thread, never on the async workers, and every file path is watched by the reload watcher; the settings hold a digest of the files' bytes, so a certificate rewritten at the same path (certbot's `live/` links) is applied on the next reload. A file that breaks keeps the last good certificate in use.
- **Let's Encrypt is opt-in.** Only `web.letsencrypt: {email}` turns it on, and writing it accepts the CA's terms. Let's Encrypt stopped sending expiry mails on 2025-06-04 and no longer stores contact addresses; the email stays required as the deliberate act and is sent, because other ACME servers use it. `burrow status`, the metrics `burrow_certificate_expiry_timestamp_seconds` and `burrow_certificate_failures_total` and the admin UI show what the mails used to say.
- **instant-acme 0.8.5, pinned,** with `ring`, `rcgen` and `time`, without aws-lc, hyper-rustls or x509-parser, through our own HTTP client on hyper and tokio-rustls. The client talks HTTPS only, follows no redirects, has a 10-second connect and a 60-second request limit and a 1 MiB answer cap, trusts webpki-roots plus `letsencrypt.ca`, and keeps instant-acme's User-Agent (Pebble requires one). It clamps `Retry-After` to 30 days before instant-acme reads it, because 0.8.5 adds the seconds to `SystemTime::now()` without a check (`lib.rs`, `retry_after`) and a hostile server could make burrow panic, and it records the `Retry-After` of a 429 or 503, which 0.8.5 drops from `rateLimited` problems. A hand-written client instead of hyper-rustls: hyper-rustls would bring a second client stack (hyper-util's legacy pool and tower) for six requests an order.
- **The account** is one per directory URL, in `<state>/acme/<hash of the URL>/`. Its key is written (0600) before the account is created, and the account is created from that key, so a crash or a failed write between "created" and "saved" finds the same account again instead of making a second one (Let's Encrypt allows 10 new accounts per IP address every 3 hours). Status shows the account URL for a CAA `accounturi` record (RFC 8657).
- **Orders.** One certificate per service for all its names, one order at a time on the server, TLS-ALPN-01 first (RFC 8737; its certificate carries the critical acmeIdentifier extension and is served only to a hello that offers exactly `acme-tls/1`), HTTP-01 on `web.http` next (RFC 8555 section 8.3), both answered before any site rule. An IP address is an `ip` identifier (RFC 8738) answered on its reverse name and ordered with the `shortlived` profile when the directory lists it; `letsencrypt.profile` is used for names only when the directory lists it, otherwise status says which profiles it offers and no order is made. Names are read from the SAN only. A new chain is used only after it parses, its key matches and it covers every name; it is written atomically to `<state>/certs/<first name>-<hash of the sorted names>/` (0700 folders, 0600 files) before it is served, and stored certificates are served at start before any network call.
- **No duplicate certificates (owner decision 0i).** Certificates are kept by their names, not by the service that ordered them. Any stored certificate from the same directory that covers all of a service's names is served, whoever ordered it, so a restart, a reload, a renamed service or a name moved to another service orders nothing; before any order, a stored certificate that covers the names and is not yet due for renewal (two thirds of its life) is used instead. The tunnel by path on a site's name adds no name of its own and uses the site's certificate. A certificate no service uses stays 30 days, so adding the name back costs no order. A guard allows at most 4 new certificates per exact set of names in 7 days, counted in `<state>/acme/<directory>/issued.json` so a restart cannot reset it; a fifth waits, and status says until when. Let's Encrypt allows 5 certificates per exact set of identifiers every 7 days, with no override, and exempts ARI renewals (an order with `replaces` for a certificate not yet replaced) from all limits, so renewals with `replaces` are not counted; one left over is for a manual order or a crash between issuing and saving.
- **Name changes (owner decision 0l, config.md 3.15 rule 6).** A name on a new service gets its own order. A name added to an existing service re-orders that service's certificate for all its names, sent with `replaces` for the old one (they share a name, so it counts as an ARI renewal); the old certificate keeps serving the names it covers, and the new name answers with the pending page until its certificate arrives. A removed name orders nothing: the certificate that covered it keeps serving the others until its next renewal, which then orders the smaller set. Orders run one at a time on the server, and status lists the queue (`acme.queue`: service, names, when, and which one runs). A stored or reused certificate that covers the names still wins over any of these orders.
- **One rule for each name's check (owner decision 0j, config.md 3.15 rule 1).** validate and the runtime both call `burrow_syntax::web::checks_for`: DNS-01 for a wildcard or `challenge: dns` (never for an IP address), otherwise TLS-ALPN-01 when `web.https` is port 443 and HTTP-01 when `web.http` is port 80, because the CA connects only to those ports (RFC 8737, RFC 8555 section 8.3; a router may forward them to other local ports). An order tries TLS first, then HTTP, within the checks every one of its names allows. A name with no possible check is never ordered; status gives the reason, and a stored valid certificate that covers it is still served. Until DNS checks exist (P6), a DNS case says they come in a later phase.
- **Renewal** follows ARI (RFC 9773): a random time in the suggested window, the next check after `Retry-After` clamped to 1 minute to 12 hours (Let's Encrypt asks for at least two checks a day), 6 hours after an answer that is not usable; `replaces` is sent while the old certificate is unexpired, and dropped only after a 409 `alreadyReplaced`. Without ARI, renewal comes at two thirds of the life, or half for certificates under 10 days (Let's Encrypt integration guide). The ARI id is built from x509-cert's AKI and serial and tested against RFC 9773's example.
- **Failures back off like Let's Encrypt asks:** 1 minute, 10 minutes, 100 minutes, then daily, plus up to a tenth of jitter, never sooner than a `Retry-After`. Every 6 hours would pause a forgotten broken name after about 384 days (1,152 consecutive failures, refilled one a day). Short-lived certificates retry at most every 6 hours while more than 2 days are left, then every 15 minutes to 4 hours, below the 5 failed authorizations per hour per name. An error is logged with under 7 days left (2 for short-lived). A failure never closes a listener or touches another service, and the old certificate is served even after it expires.
- **The staging fallback** is used only for Let's Encrypt production: after a failure, one order goes to the staging service in the gap before the next production try, and its result is a note in status ("the test service accepted the same checks"). Production keeps its own schedule; a staging success can bring the next production try forward to 100 minutes after the failure at the earliest, never sooner. A test certificate is never served. This avoids two traps of "staging until it works, then production once": a CAA `accounturi` pinned to the production account fails every staging try, and production must not fail at staging's pace.
- **The state folder** exists only with `web.letsencrypt` and is made on first write. `burrow server --state-dir DIR` names it; an installed server service passes it, and otherwise a server run by hand uses one folder per config file under the user's state folder (`dirs::state_dir()/burrow/servers/<file>-<hash>`). `burrow status` (and its JSON, `acme.state_dir`) names it. A service installed with `web.letsencrypt` gets its folder from the system: systemd `StateDirectory=burrow/<name>` with `StateDirectoryMode=0700` (systemd.exec(5): owned by `User=`, writable under `ProtectSystem=strict`, not removed when the unit stops; not under `/run`, which is cleared at boot), launchd has no such key (launchd.plist(5)), so the installer makes `/Library/Application Support/burrow/<name>` 0700 for the service account, and on Windows `%ProgramData%\burrow\services\<name>` (the service's config folder is `%ProgramData%\burrow\<name>`) owned by Administrators, with inheritance removed and only SYSTEM, Administrators and the service account (Modify) on it (icacls). Uninstall keeps the folder like the config folder and prints where it is and how to delete it; only `--purge` deletes it. Deleting it on every uninstall would lose the account and every certificate, and a reinstall would order them all again against the limit of 5 certificates per exact set of names every 7 days.
- **Accepted risks** (industry standard): HTTP-01 over plain port 80; validation from several Let's Encrypt vantage points means a firewall that allowlists or geo-blocks breaks it; no HTTP proxy for ACME (instant-acme issue 297 is open too); if Let's Encrypt drops the X1/X2 cross-signs before webpki-roots ships the Gen Y roots, `letsencrypt.ca` is the workaround.
