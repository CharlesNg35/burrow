# Decisions

Why burrow is built the way it is: each record names a choice, the options weighed and the reason, with sources where they matter. Read it before changing a design, and add a record for each new one. Something recorded here as intended is not a bug.

Short records. Newest last.

## D1. Transport: raw TCP with a data-channel pool, no HTTP/2 or QUIC as primary

HTTP/2 only lets the client open streams, so the server could not open one per visitor without a control-channel round trip anyway. It also puts every stream behind one TCP connection (head-of-line blocking), has no UDP, and brings a large pre-auth surface (HPACK, SETTINGS, flow control). QUIC is a possible future option if UDP performance matters, but it would add a large dependency and its own TLS. Default: one TCP control channel per client plus one TCP data channel per visitor connection, taken from a pre-established pool.

## D2. Pool per client, not per service

rathole keeps 8 idle channels per TCP service. Because burrow tells the data channel its target in the first frame, any idle channel can serve any service of that client. Default `pool.min_idle: 4`, adaptive up to `pool.max_idle: 64`: when a visitor finds the pool empty, the target idle count doubles; it decays by one each idle minute.

## D3. Noise_NNpsk0_25519_ChaChaPoly_BLAKE2s, one handshake per channel

Every control and data channel runs its own handshake. A full handshake (both sides, one core) costs about 118 us (benches/cipher.rs), which the pool hides from visitors. Details and proof points are in docs/protocol.md.

## D4. Cipher: ChaChaPoly default, AES-GCM opt-in, `ring` backend

Measured on an i5-12600K (AES-NI, VAES, AVX2), seal plus open in one thread (`cargo bench --bench cipher`):

| backend    | cipher      | 16 KiB chunk | 64 KiB chunk |
| ---------- | ----------- | ------------ | ------------ |
| ring       | ChaChaPoly  | 1286 MiB/s   | 1261 MiB/s   |
| ring       | AES-256-GCM | 4591 MiB/s   | 4360 MiB/s   |
| RustCrypto | ChaChaPoly  | 810 MiB/s    | 833 MiB/s    |
| RustCrypto | AES-256-GCM | 864 MiB/s    | 853 MiB/s    |

snow enables `ring` through its `std` feature anyway, so using the `ring-accelerated` resolver adds no new crates. ChaChaPoly stays the default because it is constant-time on every CPU, including ARM boards without AES instructions. A client can set `cipher: aes-gcm` to get about 3.5x on x86 servers. The server accepts both; the choice is bound into the Noise prologue.

## D5. Config parsing: saphyr-parser for YAML and JSON, our own schema checker

serde_yaml is deprecated (0.9.34+deprecated), serde_yml has had soundness and maintenance concerns, and both stop at the first error. saphyr-parser is maintained (pushed 2026-10) and gives byte, line and column markers for every event. JSON is valid YAML 1.2 flow syntax, so the same parser builds the spanned tree for both; `.json` files are first checked with serde_json so JSON-only syntax errors are reported exactly. The structural check is driven by the JSON Schema that schemars derives from the config types, so `burrow schema`, editor validation and `burrow validate` share one definition. After the tree passes, serde (with `deny_unknown_fields`) builds the typed config.

## D6. One validation engine, run everywhere

`burrow server` and `burrow client` run the same checks as `burrow validate` before opening any socket, and the server runs them on every reload. Errors are printed in the same format each time. `burrow validate` is the same engine without starting anything.

## D7. Durations as integer seconds with a `_secs` suffix

No duration-parsing crate, and the unit is obvious from the key.

## D8. Heartbeat interval is server-owned

The server sends its heartbeat interval in the welcome message. The client times out after three missed intervals, so the two sides cannot disagree.

## D9. Insecure plaintext still authenticates

With `insecure_plaintext: true` on both sides, the Noise handshake still runs (so the secret is never exposed and auth stays strong), but data channels copy raw bytes after Connect and Status. The flag is part of the authenticated prologue, and a mismatch is refused after authentication with `Bye` reason plaintext mismatch. Raw bytes carry the end of each direction as a TCP FIN, so when a target closes first the client sends the first FIN on the data channel and holds its TIME_WAIT, unlike encrypted channels, where the server closes first. A client that sustains several hundred such connections per second can run out of local ports; use encrypted mode there, or allow reuse with `net.ipv4.tcp_tw_reuse=1` on Linux.

## D10. Data plane: data-channel pool, not a multiplexed connection

Evidence from code: frp turns yamux on by default (`tcpMux: true`), and chisel multiplexes SSH channels on one WebSocket. Both put every visitor behind one TCP flow-control window. rathole, like burrow, uses one TCP connection per visitor.

Evidence from measurement (docs/benchmark.md): frp is the cleanest experiment, because multiplexing can be switched off in the same code. Without tcpMux, frp's 4-stream throughput rises from 8.8 to 36.0 Gbit/s and its p99 echo latency under a 2 Gbit/s background load drops from 678 to 383 µs (head-of-line blocking gone), but new connections per second fall from 10.0k to 2.9k, because each visitor waits for a fresh TLS connection. A pre-opened pool keeps the first benefit without the second cost: burrow does 33.4 Gbit/s, a p99 of 549 µs under the same load, and 13.5k connections/s.

## D11. Record size: full 64 KiB Noise records for bulk data

Measured with `bench/run.sh` (burrow only, 2 runs each). Single-stream iperf3 through the tunnel: 8 KiB chunks 7.7 Gbit/s, 16 KiB 10.1, 32 KiB 12.2, 65519 B (largest Noise message) 12.8. With 4 streams: 23.0, 28.5, 32.8, 34.7. Small-message latency was unchanged (p50 61 µs in every case) because short reads are sealed from a 512-byte stack buffer. Big buffers exist only while data is flowing: a pump drops them when the socket has no data ready, so idle connections hold no large buffers.

## D12. Allocator: system malloc, except on musl

With mimalloc: throughput unchanged (12.6 vs 12.8 Gbit/s single stream), new connections per second +3% (14.1k vs 13.7k), but RSS with 10k idle connections rose from 167 MB to 273 MB. The cost outweighs the gain, so glibc, macOS, Windows and FreeBSD builds keep the system allocator.

The release Linux binaries are static musl builds, and musl's mallocng fragments under connection churn: in a soak the RSS of a server grew from 6.3 to 16.2 MB in under 2 hours while its live heap stayed at about 1.4 MB. Musl builds therefore use jemalloc (x86_64, aarch64 with 64 KiB pages allowed, riscv64), and mimalloc on 32-bit ARM, where jemalloc does not build with zig. With them the same soak stays flat.

## D13. insecure_plaintext copy path

`tokio::io::copy` uses an 8 KiB buffer: 14 Gbit/s single stream, behind rathole's plain TCP (16). A 64 KiB buffer reached 33 Gbit/s (69 with 4 streams), but a `BufReader` would hold 64 KiB per direction for the life of the connection (about 2.6 GB at 10k idle connections). The raw pump therefore uses the same lazy scheme as the encrypted path. Same throughput, and 10k idle connections cost 172 MB, the same as encrypted mode. The 128 KiB record-reader buffer is also freed once the plaintext stream takes over.

## D14. Listen backlog 4096

std and mio listen with a backlog of 128. A burst of 300 visitors overflowed it (`TcpExtListenOverflows`, "Possible SYN flooding" in dmesg), and some visitors were reset. All listeners are now created with a backlog of 4096, capped by the kernel's `somaxconn`.

## D15. Deferred: pinned-key NK mode and WebSocket transport

NK with a pinned server key plus an inner token would be a second authentication mode next to NNpsk0, which already authenticates both sides without extra key material. Not worth the extra security surface. A WebSocket-over-TLS transport needs rustls, webpki roots and tungstenite on the client, roughly doubling the dependency tree and the pre-auth parsing surface, for networks that only allow HTTPS. HTTP CONNECT and SOCKS5 proxy support already covers many restricted networks. Both stay out until there is a concrete need. The transport is isolated in `handshake.rs` and `src/transport/`, so either can be added later behind a config option. WebSocket was added later, see D17.

## D16. Leak hardening

Long-running behaviour is tested by state, not only by RSS. `tests/heavy.rs` churns TCP connections, UDP peers, client reconnects and reloads, and asserts that sessions, waiting visitors, UDP peers, open file descriptors and live tokio tasks return to their baseline after every round. This found and fixed: control-channel writer tasks that outlived a timed-out session, UDP relay tasks orphaned when their future was cancelled, stale pool waiters, client data channels that survived a client stop, and UDP peers that expired while traffic still flowed in one direction.

## D17. WebSocket transport, opt-in

Some servers can only be reached through an HTTP(S) reverse proxy or a CDN. For those, clients connect over WebSocket (RFC 6455) instead of raw TCP. The feature is off unless the server config has a `websocket` section, and a server configured for WebSocket only opens no TCP control port.

- **WebSocket over HTTP/1.1, not HTTP/2 streams or gRPC.** It passes through every common proxy and through Cloudflare. HTTP/2 extended CONNECT (RFC 8441) is rarely supported by proxies.
- **One WebSocket per data channel, taken from the same pool.** This keeps the head-of-line properties of D10. shellcn multiplexes yamux over a single WebSocket; burrow does not.
- **Noise runs inside the WebSocket.** A TLS-terminating proxy only sees Noise records, and the URL, path and headers grant nothing.
- **No MASQUE (RFC 9298).** CONNECT-UDP needs an HTTP proxy that relays UDP itself, mostly over HTTP/3. burrow already carries each datagram as its own record inside a data channel, so UDP services work over WebSocket unchanged, with the usual UDP-over-TCP latency on packet loss.
- **Keepalive.** Proxies close idle WebSockets (nginx after 60 s by default, Cloudflare after 100 s), and some only count data frames. The server therefore sends an encrypted keepalive record on idle pooled channels every 25 s. A test with an idle-killing proxy fails without it.
- **Crate: tokio-websockets 0.13** (strict RFC compliance, maintained, uses the aws-lc-rs backend that rustls uses, D55), plus tokio-rustls, webpki-roots and httparse. The request head is parsed before the upgrade, so wrong paths are refused with 404 and nothing else is exposed.
- **Optional own TLS** (`websocket.tls.cert`/`key`), for servers without a proxy. Clients trust the public roots plus an optional `ca` file.
- **Cost, measured** (docs/benchmark.md, loopback): about 93% of the TCP throughput (11.75 vs 12.62 Gbit/s single stream), 12.0k vs 13.5k new connections per second, and about 1.8x the idle memory at 10k connections (391 vs 220 MiB), from the library's per-connection frame buffers. That is still well below frp (796 MiB) and chisel (719 MiB), which also uses WebSocket.

## D18. Reconnect: never give up by default

Clients retry forever with jittered backoff (250 ms up to 30 s, reset after 10 s of stable connection). DNS is re-resolved on every attempt, so moving the server and updating DNS needs no client change. Addresses are dialed with Happy Eyeballs (RFC 8305: interleaved families, the next attempt 250 ms after the previous one, first success wins), so a stale or black-holed address costs 250 ms instead of the whole connect timeout. An address that accepts TCP but then fails the TLS, WebSocket or Noise step (a load balancer with no backend, an address now used by another host) is tried last from then on, and the address of the last good handshake is tried first, so data channels follow the control channel. During an outage the client logs the first failure and then a summary once a minute. `reconnect.give_up_after_secs` and `reconnect.on_rejected: exit` exist for setups where a supervisor should notice; neither is written by `init`. A rejected client keeps retrying by default, so fixing the server config later brings it back without touching the client machine.

## D19. Default ports 7835-7840

2333 is rathole's default, and 8080, 8081 and 8443 are among the most used ports on any host. burrow uses its own block, none of which is in the services database: 7835 for TCP clients, 7836 for WebSocket behind a proxy (bound to 127.0.0.1), 7837 for WebSocket with its own TLS, 7839 for the local `burrow admin` UI, and 7840 for the example service written by `init`.

## D20. `burrow service` instead of shipped unit files

Hand-written unit files go stale, differ per OS, and leave the hard parts to the user: a service account, file permissions, secrets that `sudo` dropped, log rotation, and updates. `burrow service` does them the same way on every platform, much like `cloudflared service install` and `tailscaled install-system-daemon`.

- **Admin only, system services only.** A per-user service would stop at logout on Linux and macOS. One install path keeps it simple.
- **A dedicated account, created by burrow.** `burrow` (useradd `--system`), `_burrow` (dscl, hidden, id below 500), or a Windows virtual account, which Windows creates with the service. Running as root would give an attacker who gets through the pre-auth parsers the whole machine. The account and the copied binary are removed by the last `uninstall` that used them.
- **Copies, not references.** The config is copied to the service's own folder, `/etc/burrow/<name>/<role>.yaml` (`%ProgramData%\burrow\<name>\` on Windows), and the binary to `/usr/local/bin`, because a service must not depend on, or run code from, a folder a normal user can write. The binary is always copied, even from a root-owned folder, so a service never depends on where burrow was downloaded (a 0700 `/root` would make systemd fail with 203/EXEC for the service account) and always runs from one predictable path; there is no official package to defer to, and the unrelated Debian package named `burrow` rules out guessing a package path. When users other than root can write `/usr/local/bin` (Homebrew on Intel Macs), the service gets its own copy in a root-only folder instead. If that folder turns writable after the install, the service stays manageable (status, logs, stop, uninstall, list), but burrow no longer runs or replaces the binary there; `service status` and `update` name the reinstall that moves it to the root-only copy. Accepted risk: until that reinstall, a service installed with `--run-as root` still starts the binary in that folder as root, and `sudo burrow` in the hint runs whichever `burrow` is first on PATH; this is the same for every root daemon and every `sudo` use under a user-writable `/usr/local` (Homebrew).
- **Checks before changes.** The config is validated, every listen port is test-bound and its owner is named, and the instance lock is tried before anything is written. A failed reinstall restarts the previous service.
- **Own log files** with size-based rotation (10 MB, 5 files) rather than journald or the Windows event log, so `burrow service logs` works the same everywhere and a log cannot fill the disk. Startup failures are written there too, so a Windows service that has no console still says why it stopped.
- **Updates:** `burrow service update` replaces the binary only when it is newer, keeps the previous one, restarts every affected service and rolls back if one does not come up. `burrow update` downloads a release itself (D29).
- **Crates:** `windows-service` (Mullvad) for the Windows dispatcher and SCM; systemd and launchd are driven through `systemctl` and `launchctl`, which are their stable interfaces.

## D21. Ask only for what burrow cannot know, but write every field

`listen` says where the server binds on its own machine, usually `0.0.0.0`. Behind NAT, a cloud firewall or DNS it says nothing about how clients reach it, so the client address is never guessed from it. `client-config` takes it from `--server`, or from the optional `public_address` in the server config, so it is typed once for all clients, and otherwise stops with a hint. A host alone gets its port from `listen`, which is the one thing `listen` does tell. `0.0.0.0` is refused; loopback and private addresses are allowed with a note, because tests, LANs and VPNs need them. Notes only warn about something that may not work.

Config files accept short forms (`listen: 7835`, `target: 3000`, `server: host`), but required fields stay required, and `init` still writes `listen`, `bind`, `target` and `allow` in full, because a generated file is also the user's documentation. `init` writes `public_address` only when `--server` is given, because a placeholder would be an invalid value. WebSocket stays off unless its section is written.

## D22. Visitors: private by default, `reach` as an opt-in

Some services should not be public at all: a database, SSH, an admin page. frp (`stcp` with a visitor) and rathole leave this to a second tool or a firewall rule. burrow lets the server relay a visitor to a client without opening a port.

- **The server's config still decides.** A service without `bind` is private, and lists its `visitors`. A visitor reaches only those services, so a leaked visitor secret exposes what was listed and nothing else.
- **`reach: { CLIENT: any }` is the explicit opt-in** for `ssh -L`-style access, where the visitor picks the target. It is bounded by the client's `allow` list, which the client owner controls and which a compromised server cannot widen. `validate` warns about every `reach: any`, because `init client` writes a broad `allow: [127.0.0.0/8]`.
- **Visitors are not clients.** They have their own section, secrets and limits, they never expose anything, and their names are looked up only for visit channels, so a visitor secret cannot open a client session or the other way round. The same constant-work rejection hides which names exist.
- **One channel per local connection**, with the same handshake as data channels. A visitor keeps no long-lived connection, so it has nothing to reconnect, and the server keeps no state for an idle visitor. The cost is one handshake per connection plus one round trip, because the visitor waits for the server's answer before sending data so that a refusal always carries its reason. The server also decrypts and re-encrypts every record between the two channels: on one loopback machine a visit carries 7.8 Gbit/s on one stream and 22.7 Gbit/s on four, against 12.9 and 35.0 for a public service.
- **`local` defaults to `127.0.0.1`,** unlike `bind` on the server: anyone who can reach a forward uses the visitor's access, so sharing it with a network has to be written out, and `validate` warns about `0.0.0.0`.
- **Reload revokes**: open visits re-check their request when the config changes, as a removed client's connections do.
- **TCP and UDP** since v0.1.2: see D42.

## D23. Port ranges are one service

A range like `bind: 30000-30010` stays one service with a first port and a count, instead of eleven generated services. `max_connections`, `bandwidth`, metrics and logs then describe what the user wrote. Each public port has its own listener and maps to the same position in the target range; a visit request carries the index. A range holds at most 1000 ports, so a typo cannot open tens of thousands of sockets.

## D24. PROXY protocol written by the server

The server knows the real source address, so it writes the PROXY v1 or v2 header into the tunnel right after Connect, and the client forwards it as data. Clients need no change, the same code covers visits (with the visitor's address), and the header works in `insecure_plaintext` mode too. It is off by default and per service, because a target that does not expect it fails on the first bytes. Checked against nginx `listen ... proxy_protocol` with both versions.

## D25. Several clients, and health checks through the tunnel

A service can list several clients. `failover` takes the first connected one, `balance` rotates new connections, `least_connections` takes the one with the fewest open connections; an open connection never moves. Health checks run on the server and use the tunnel itself: a normal Connect to the target through each client, closed at once. This needs no client config, tests the real path including the client's allow list, and works with any target the client can reach. A client is down after `failures` failed checks in a row and up again after one success. When no client passes, connections still go to a connected one, so a broken check cannot take a working service down.

`balance` is smooth weighted round robin as nginx does it ([ngx_http_upstream_round_robin.c](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_upstream_round_robin.c), introduced in [nginx commit 52327e0](https://github.com/nginx/nginx/commit/52327e0627f49dbda1e8db695e63a4b0af4448b1), "Upstream: smooth weighted round-robin balancing", whose message gives the same example). On each new connection every healthy client adds its weight to a running score; the highest score goes first and loses the sum of the weights. With weights 5, 1 and 1 the order is a a b a c a a, so a heavy client never takes a long run of connections, and with equal weights it is plain round robin. A client entry is a name or `{name, weight}`, weight 1 to 1000 (the cap catches a typo like 10000), and a weight is refused with the other modes, where it would mean nothing. The scores are kept per service and start again when its clients or weights change. `least_connections` counts the open connections per entry (a client and its target) of this service, as 0zc below keeps open counts per entry. A tie goes to the first client in the list, without a rotation. The count goes up when a client is picked, before its connection is set up, so two connections arriving together go to two idle clients. Both modes pick only among the clients that the failover order puts first (healthy and not set aside); the others stay behind them as fallbacks. No other strategies (random, a score): nobody has asked for them. Hashing on the source address came later as `ip_hash`, with rendezvous hashing so that a client going away moves only its own visitors (D65).

A `clients` entry may also name its own target, `{name, target, weight}`, so one client in front of several machines can spread a service over them (owner, 0zc). What the server balances is then an entry, a client and its target (the entry's own, or the service's), and the server sends that target in the Connect, so the protocol does not change, older clients work and the client's allow list still decides. Health checks, open counts, balance scores and set-aside standing are kept per entry, so a VM that stops answering takes only its own entry out. A client repeats only with another target, and an entry's port range has the service's size, so a port index maps the same way. An entry without a target or weight is written as a plain name, and the admin schema gives the list a new type (`ref_entries`) without a fallback, so an older admin UI edits it as raw YAML, which the server checks, instead of a list of names that would drop the targets.

Without health checks, the server still learns from real connections. While it waits for the client's answer it keeps a copy of what the visitor sent (up to 64 KiB, then it stops reading until the answer), so when a client answers that it cannot connect, cannot resolve the target or refuses it, the same connection goes to the next client and the visitor notices nothing. A client that does not answer in time counts as failing too, but its connection moves on only if the visitor has sent nothing yet: the client may still deliver those bytes, and a request must never reach the target twice. A channel that breaks says something about the session, not the target, and counts for nothing; a client that cannot hand over a data channel in time is set aside like one that does not answer, for TCP as for UDP. A refusal comes from the client's config, which only changes when it reconnects, so that client is skipped for the target until then; a target it could not reach is skipped for 10 s, doubling up to 60 s while it keeps failing, and the first success clears it. Skipped clients stay at the end of the list and are still tried when all others fail. A service with one client keeps no copy and works as before. This is what nginx does by default (`proxy_next_upstream`, `max_fails`), and it avoids probing every target through every client every few seconds, which shows up in the target's logs.

A connect that fails because the client's own local port is in use (Windows `WSAEADDRINUSE`, which `connect` returns when its implicit bind finds the address taken, [Microsoft Learn: connect](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-connect)) is not the target's fault: it happens on Windows under connection churn to one target, because the client closes first and its ports sit in TIME_WAIT ([port exhaustion](https://learn.microsoft.com/en-us/troubleshoot/windows-client/networking/tcp-ip-port-exhaustion-troubleshooting), reproduced in [SocketCloseTest](https://github.com/CompareAndSwap/SocketCloseTest)). The client tries again up to 3 times with a new socket after 5 ms each, and if it still fails answers `6 offline`, so the connection moves to the next client and nobody is set aside. `WSAEADDRNOTAVAIL` stays a target error, since on Windows it means the remote address is invalid. SO_REUSEADDR is not set: on Windows it lets a socket take a port another one is using.

A website can ask for an HTTP check instead (`health_check: {path: /healthz}`). It runs the same Connect through each client and then sends one `GET` of the path over that channel, through the site's own `target_tls` with the same verification as visitors' requests. It sends only `Host` (the site's first name that is not a wildcard, else the wildcard's parent), `User-Agent: burrow-health-check/<version>` and `Accept: */*`, as Kubernetes probes do ([configure probes](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)). It never passes through the site's stages or the access log, and it never counts in the service's metrics. Any 2xx or 3xx answer is up, as in Traefik, NGINX Plus, HAProxy and Kubernetes ([Traefik health check](https://doc.traefik.io/traefik/reference/routing-configuration/http/load-balancing/service/), [NGINX health_check](https://nginx.org/en/docs/http/ngx_http_upstream_hc_module.html)). Redirects are not followed, which is Caddy's default ([reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)). 401 and 403 count as down, so the path must not need a login. The check reads only the response head and does not wait for the body. A Connect answered `ok` clears the "could not reach" standing above, because the target is reachable. The HTTP answer then decides only up or down, so an app answering 500 leaves its client down without also setting it aside. Status shows why the last check failed. The gRPC health protocol (`grpc.health.v1`) is not in v0.2.0: it needs protobuf and a gRPC layer, so gRPC sites keep the TCP check.

## D26. Bandwidth limits

One token bucket per service and direction, shared by all its connections and ports, refilled continuously with a burst of 100 ms (at least 16 KiB). TCP waits for tokens, so senders slow down through normal backpressure; UDP has no backpressure, so datagrams over the rate are dropped, as a router would. Throughput, latency and connection rate without a limit are unchanged (measured against the previous commit).

## D27. Metrics off by default, one snapshot for everything

The metrics endpoint is off unless `metrics.listen` is set, defaults to `127.0.0.1`, and `validate` warns when it is reachable from the network, because it shows client, service and visitor names and traffic. The server builds one status snapshot; `/metrics` renders it as Prometheus text and `burrow status` reads it as JSON from a local endpoint only it can use, so the two can never disagree. The metrics port serves nothing else: the JSON holds more than a scraper needs, such as client addresses. Counters are relaxed atomics updated per read, with no measurable cost.

## D28. A SOCKS5 forward for visitors

`reach` lets a visitor pick any target its client allows, but one forward per target is tedious. A SOCKS5 forward (`socks: true`, or `visit --socks`) reads the target from each SOCKS request and sends it as a normal reach request, so the server and the client's allow list decide exactly as before. CONNECT and, since v0.1.2, UDP ASSOCIATE are supported, without authentication: the listener is on `127.0.0.1` by default, like any forward. See D42 for UDP.

## D29. Our own updater instead of a crate

`burrow update` downloads a release with the TLS, proxy and HTTP pieces burrow already has, checks it against `SHA256SUMS`, runs it to confirm its version, and hands it to `service update` for rollback. The `self_update` crate would have added 2.3 MB (42%) and about 100 crates to the binary and ignored burrow's proxy settings; the own code adds about 110 KB and one small dependency for gzip.

## D30. WebSocket channels end with TLS close_notify

A data channel over `wss://` used to end by dropping the connection. A TLS proxy in front of the server can treat that as an error and drop the last message of the stream under load, which a test reproduced (80 KB missing out of 8 MB). Channels now shut down the TLS layer below the WebSocket, which sends close_notify and a FIN. A WebSocket Close frame as well would cost 3-5% of new connections per second for no benefit, because the record layer already marks the end of each stream.

## D31. Clients and visitors reload on save, like the server

Everything that changes often lives in the server config, so clients were first left to apply changes on restart. That cut every open connection for what is usually an `allow` edit. Clients and visitors now watch their file (and take `SIGHUP`) through the same reload loop as the server: the new file is checked like `validate`, and a file that does not load is rejected while the running config stays. A client compares field by field: `allow`, `server`, `name`, `secret`, `headers`, `ca`, `cipher`, `proxy` and `insecure_plaintext` make it reconnect, the rest applies to the next connection. `allow` reconnects because the server skips a client that refused a target until that client reconnects (D25); a protocol message could avoid that, at the cost of a wire change right before a release, and the reconnect costs about a second. Connections that are being set up at that very moment fail (measured: a few dozen at 64 parallel connection attempts), since the data channels of the old session close with it. Open connections run on their own data channels and survive the reconnect, except those whose target the new `allow` no longer permits, which are closed as on the server. A new `server` or `name` first takes the instance lock of the new identity, so a reload cannot make two clients run the same tunnel. A visitor has no session: connection fields apply to new connections, and only the forwards that changed are closed or opened.

## D32. A visitor asks the server for its own config

`burrow visitor-config` needs the server config, so a visitor depended on the server's admin for every change. The visit channel now answers one more request, "what may I use?", after the same handshake and secret check as a visit, with the same grants that `visitor-config` writes (one function decides both, so they cannot differ). `burrow init visitor` uses it for a new file, and `--update` merges it into an existing one: forwards you have keep their local ports and names, new grants get free ports, revoked ones are removed, the changes are shown before anything is written, and only the `forwards` block of a YAML file is replaced, so other lines and comments stay. To say what `reach` means, a client sends its `allow` list once per session; the server shows it only to visitors with `reach` for that client, who may already use any target it permits.

## D33. Admin over the visit channel, never a new port

`burrow admin` edits a running server's config from a browser on the admin's machine. The server exposes nothing new: an admin channel is a visit channel with the visitor's secret and a different first request (protocol section 11), so it gets the same anti-enumeration handshake, deadline and limits, and a visitor without rights gets the same `5 forbidden` as any refused visit. Rights are opt-in per visitor in the server config, `admin: read | write`, optionally limited to source addresses with `admin_from`. Only these two levels exist; finer rights can be added later as a new field. A write admin without `admin_from` gets no warning, because that is the simple setup most people run. `validate` warns when an admin visitor also uses services or `reach`, since one leaked secret should not give both. On every reload the session checks its visitor again and ends when the right, the secret or the source is gone, or the level changed. An installed server can write its own config only when it has an admin visitor (or `service install --admin-writable`): then the service account owns the service's config folder and the sandbox lets it write there, and otherwise root owns the folder, the sandbox stays as tight as before and the UI says honestly that it is read-only, with the exact command that changes it. Every service has that one folder from its first install, so switching admin writes on or off only changes the folder's owner and nothing moves; installing again from the installed config itself (`-c /etc/burrow/<name>/server.yaml`) is allowed and reinstalls that service, because the downloaded source may be gone and the installed copy is the truth. The env file with secrets stays outside the folder (`/etc/burrow/<name>.env`), so a writable folder never holds it. Before each admin write the previous file is kept beside it (`.server.yaml.history/`, the last 20, mode 0600), so a change can be reverted; when that folder cannot be written the history is kept in memory only.

## D34. Schema-driven admin UI with semantic types; completeness by derive

The server describes its config to the UI as a schema of semantic types (`ip_port`, `target`, `cidr_rule`, `ref<client>`, `ref_list<visitor>`, `duration`, `rate`, `secret_ref`, ...) with relations such as "only for TCP services" or "one of client and clients". It never names a widget; the UI decides that a `ref_list<client>` is a multi-select of the clients with their online state. Core screens are laid out by hand and place fields by key, and every field they do not place, including fields a newer server adds, is rendered by a generic renderer from the same types. Types a UI does not know come with a `fallback` chain ending in a text input that the server validates, so an older UI keeps working against a newer server and never shows a broken field. The schema comes from the config model through `#[derive(AdminSchema)]`: every field and every enum variant must carry `#[admin(...)]` or `#[admin(skip = "reason")]`, otherwise the build fails on that field, and the macro checks that the semantic type fits the Rust type. Descriptions and ranges are read from the existing `schemars` and `serde` attributes, so they are written once. The model lives in the crate `burrow-config`, shared by the server and the UI, and the derive also emits a typed path for every field (`ServiceEntry::BIND.of("web")`), so the UI and the server's admin code never name a config field by string, `cargo xtask arch-check` refuses such a string, and a renamed field fails to compile at every use. The UI still renders from the schema the server sends: the typed paths only name fields, and a field the live schema lacks is left out. Server-delivered UI code was rejected: the browser runs only the UI embedded in the local binary.

## D35. Comment-preserving patcher with verification

An admin change is a list of operations on paths, never text. The server applies them to the raw tree of the file and turns the difference into byte edits on the spans of the existing parser: a changed value replaces its span, a new key is inserted after its siblings with their indentation, a removed key takes its leading comment block with it, and the BOM, line endings and every other byte stay. Each result is parsed again and must give exactly the wanted tree; otherwise nothing is written. The result is then checked by the same function as `validate` and reload, the plan with its diff is shown, and the write uses the same atomic, revision-checked save as `burrow edit`. Accepted risk: on Windows that save writes the file in place, so its ACL and owner stay; it first writes a spare copy beside it, and when the config then fails to parse, the error names the spare to restore from. An atomic `ReplaceFileW` would need unsafe code, which waits for the owner's decision. JSON files have no comments and are re-rendered in key order with their indentation. When a change cannot be placed in the file's own layout, only the top-level section it touches is re-rendered and the plan names it (`reformat`); the whole file is re-rendered only when changes in several sections cannot be placed. A second YAML library (`yaml-edit`) was considered and rejected: two parsers could disagree on files that `validate` accepts, and it adds 150-250 KB.

## D36. Local UI security: loopback, fragment token, no cookies, Host/Origin checks

`burrow admin` listens on `127.0.0.1:7839`, or on a free port with a note when 7839 is taken (`--port N` is strict, `--port 0` always picks a free one), and never on another address. Each session serves its pages, routes and `/api` under a random 128-bit path prefix (`/r-<hex>/`), made new when a session starts and kept with it for up to 12 hours (D40), so a process that held the port earlier cannot have its poisoned cache entries match this run's URLs, and `/api` is reachable only under the prefix, never from a cached page at a fixed path. Every file is served `Cache-Control: no-store` and the pages add `Clear-Site-Data: "cache"`; remote use goes through `ssh -L`. A 256-bit token is required as the first WebSocket message; it reaches the browser in the URL fragment of a 0600 launch file in the user's own folder, so it is never on a command line, in a request or a Referer, and the page removes it from the address bar. There are no cookies, which are not isolated by port, and no CORS headers. Every request must name the local host and port in `Host` (against DNS rebinding), the WebSocket upgrade must come from exactly that `Origin`, and a request whose `Sec-Fetch-Site` is not `same-origin` or `none` is served only as a top-level navigation (`Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`, as when the browser arrives from the launch file or a link), never as a script, style, fetch or `/api` request; a navigation straight to an asset URL is served too, but asset URLs exist only under the session's 128-bit prefix, which another site cannot know; framing is denied, and `/api` always needs the exact `Origin` and the token. Pages carry a strict CSP without inline scripts, and server-provided text is only ever inserted as text. The bridge in `burrow admin` passes admin messages through without reading them, so it does not have to change when the protocol grows. Accepted risk: with a fixed default port, a hostile local user who once served the browser on 7839 and kept that connection open can answer the first request of a later run; burrow accepts this, as tools with a fixed local port and a token do (Jupyter on 8888).

The user's own folder is `$XDG_RUNTIME_DIR/burrow` when that folder is absolute, owned by the user and mode 0700, as the XDG Base Directory spec requires of it (https://specifications.freedesktop.org/basedir/latest/, "MUST be owned by the user ... Its Unix access mode MUST be 0700"); otherwise `burrow-<uid>` in the temp folder (`$TMPDIR` is per user on macOS), made 0700 and refused unless it is a real folder the user owns with no group or other rights; `%TEMP%\burrow` on Windows, which is per user. The spec suggests a warning when the variable is missing; burrow falls back silently, because the replacement is checked to the same standard. The shared instance folder (`/tmp/burrow-instances`, mode 1777, used for locks and `burrow status`) is trusted only when root or the user owns it, since the owner of a sticky folder may delete and replace any file in it; a user who finds it owned by someone else keeps locks and status files in their own folder.

Header values that carry credentials are shown by name only on every surface that masks secrets: the state sent to read and write admins and `burrow mcp`, plan and history diffs, change summaries and the INFO `config changed` log line. The list is defined once in `burrow-syntax::secret_fmt`: `Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie`, and names ending in `-Key`, `-Token`, `-Secret`, `-Password` or `-Auth`, in `request_headers` and `response_headers`, case-insensitive. A `${VAR}` value shows its variable name, never the resolved value. This follows Caddy, which logs `Cookie`, `Set-Cookie`, `Authorization` and `Proxy-Authorization` as `REDACTED` (https://caddyserver.com/docs/caddyfile/directives/log), Kubernetes client-go, which masks `Authorization` in its request logs (`maskValue` in https://github.com/kubernetes/client-go/blob/master/transport/round_trippers.go), and Traefik, which drops headers from access logs unless set to keep or redact (https://doc.traefik.io/traefik/observability/access-logs/); the suffixes cover the API-key headers apps use. A change to such a value shows as `«hidden, changed»`, so the change stays visible without its value.

## D37. Leptos CSR, own design system, built once and embedded

The UI is Rust compiled to WebAssembly with Leptos in client-side rendering mode, so it shares the value parsers with the server and the product stays one language. Leptos has fine-grained signals, which suit large live forms and once-a-second status, and it is the most used and documented Rust web framework; Yew and Dioxus are larger or slower to update, Sycamore has few users. The component kit is our own small set of controls with plain CSS and design tokens: the main Leptos kit is pinned to an older Leptos and its look would have to be fought. CI builds the WebAssembly once, compresses it and embeds the same bytes into every release target, with a size budget; a plain `cargo build` without the wasm toolchain embeds a placeholder page instead.

## D38. `self`: the server as its own client, behind two gates

A server often runs next to things worth exposing (a database, a web app, its own LAN), and needing a client process on the same machine for them was pointless. `self` is one reserved name: the client of a service, a key of `reach`, and a config section, and a real client named `self` is refused. It is implemented as a client that runs inside the server: a connection for `self` gets an in-memory channel whose other end is served by the same target code as a remote client (DNS, allow check after resolving, reach rules, Unix sockets, UDP peers, closing what a reload no longer permits). Routing, failover, health checks, limits, the PROXY header and the relay do not know the difference, because they see a channel like any other. The channel carries the usual records unencrypted (a zero tag, same framing, so an end of stream still differs from an abort); only the in-memory pair can be built that way, so no network transport and no config flag can reach it.

- **Two gates.** A visitor's `reach: self` rules are checked first, then `self.allow`, so the effective set is their intersection, as `reach` and a client's `allow` list are for remote clients. Without `self.allow`, `self` services reach their own target and `reach: self` is a validate error. `self.allow` covering a whole address family is warned about, like `allow_all` on a client.
- **What the server never dials for itself:** its own listen, WebSocket and metrics addresses over TCP (any address of this host on such a port when it listens on all of them), and link-local or cloud metadata addresses (169.254.0.0/16, fe80::/10, the AWS IPv6 endpoint fd00:ec2::254 and Alibaba's 100.100.100.200) unless `self.allow` names the address on its own; a range covering them does not count. One function decides this for `validate`, the admin UI and the data path. Another machine's address on that port stays allowed, and so does a NAT-hairpin public IP that no interface carries, as it would be for a remote client, since that listener is public anyway.
- **Status:** `self` is listed as a client marked `local`, always connected, whenever the config uses it; remote clients keep their exact JSON.
- **Cost, measured on loopback** (iperf3 and loadgen): 22 Gbit/s on one stream, 71 Gbit/s on four, 16-18k new connections per second, against 13 and 36 Gbit/s and 14k for a remote client on the same machine, which was unchanged by the seam.

## D39. burrow admin reduces admin power but never grants it

A stolen admin secret or browser session must not be able to make itself permanent, so nothing that decides who may administer can be widened through burrow admin: a new admin, `read` to `write`, a new secret on an admin visitor, a wider `admin_from` (checked against the union of the old ranges, an empty list meaning everywhere) and a renamed admin visitor are refused on every plan path, revert included, and need a file edit (`burrow edit`, an editor or ssh). The base is the current file, not the running config, since only someone with file access can put a grant there; when the file fails its checks, a grant is refused if it widens either the running config or the file's raw tree, so a broken file cannot open a way around the check. Reducing stays possible from the UI, so a leaked admin can still be revoked from there. The fields are marked `reduce_only` in the schema, so the UI offers them only towards less power through the same decision the server uses. Limit: a write admin can still change services, `reach` and everything else, so this keeps the attacker from staying, not from acting. **Environment and file references (wave 3 review, W3-E1).** Every config string is expanded from `${VAR}` before use, and some strings leave the server: answer headers and redirect targets go to visitors, request headers to an app the admin chooses, the Let's Encrypt email and profile to the ACME server, the acme-dns and RFC 2136 fields to their servers. So an admin plan may keep or remove `${VAR}` and `file:` references but never add one: at every path of the new document the references must be ones the current file already has at that path (after renames), on every plan path, revert included; moving one to another path counts as adding. DNS secrets, servers and the acme-dns address are locked outright. The validate summary, status and the Overview print references as written, never their values. **Uploads (owner decision 0w).** A write admin may upload a certificate with its key, a CA or a revocation list instead of naming a file: the server checks it, keeps it in its state folder under a name made from its contents (`pair-`, `ca-` or `crl-` and 16 hex digits), and the config holds only that name, in its own field (`upload`, `ca_upload`, `crl_upload`) beside the locked path field. So the path locks stay as they are: an upload can only name a file burrow wrote itself, validate refuses a name of the wrong kind or one that is not in the folder, and a field takes a path or an upload, never both. An uploaded CA changes whom burrow trusts (devices for `client_auth`, the ACME server for `letsencrypt.ca`), as adding a password user changes who gets in; that is within a write admin's power. The key is never sent back, logged or audited.

## D40. burrow admin keeps its session for 12 hours

A browser tab used to outlive its `burrow admin`: the next run made a new token and path prefix, so the old tab retried forever and a new tab opened each time. Now the token, the path prefix and the port of a run are kept in a 0600 file in the user's own state folder (`~/.local/state/burrow/admin-sessions` on Linux, the local app data folder elsewhere), one per visitor config, the same model as Jupyter's runtime file. The next `burrow admin` for that config reuses them while the file was used in the last 12 hours, so an open tab reconnects by itself, and expired session files are deleted the next time burrow admin starts; when an open tab reconnects within 3 seconds of the start, no new tab is opened and the terminal says so. A tab that reaches a `burrow admin` which refuses its token or no longer serves its prefix stops retrying and says that its session ended; while nothing listens it says that `burrow admin` is not running and retries every 2 seconds. Accepted risk: the token is at rest in a file only the user can read, and an open tab sends it to whatever listens on that local port while `burrow admin` is stopped, so a hostile local user who takes the port in between can learn it and use it until the session expires; this is the risk Jupyter accepts for its token file and fixed port, and D36 already accepts a hostile local user on the port.

## D41. macOS builds signed with burrow's own certificate

With the macOS application firewall on, a program that listens is allowed or blocked by its code signature. An unsigned build only has an ad-hoc signature tied to its exact bytes, so every `burrow update` looked like a new program: the firewall asked again, and on a Mac with nobody logged in it blocked the updated service silently and kept it blocked (measured on macOS 14). Release builds are therefore signed in CI with one self-signed code-signing certificate (`scripts/macos-signing-cert.sh`, repository secrets `MACOS_CERTIFICATE` and `MACOS_CERTIFICATE_PASSWORD`) and the fixed identifier `com.github.charlesng35.burrow`; the firewall then asks once per install path and keeps the answer across updates. A tagged release fails rather than publish an unsigned macOS build. The certificate must never be replaced, or every Mac asks again. It does not make Gatekeeper trust a browser download; that needs a paid Apple Developer ID and notarization, which can be added later without changing this identity's role.

## D42. UDP for visitors, and SOCKS5 UDP ASSOCIATE

A visitor reaches private UDP services and UDP targets in `reach`, with the same server-side checks as TCP. The client is unchanged, so v0.1.0 and v0.1.1 clients serve UDP visits.

- **The data path:**
  - A UDP forward has one socket per local port. Its first datagram opens one visit channel (VisitRequest flag bit 1, protocol.md section 9). The channel carries the records of a UDP service (`peer:u32 || datagram`), with peer ids chosen by the visitor and passed on unchanged.
  - The server admits at most `udp.max_peers` peer ids per visit, takes the service's bandwidth (D26) for a visitor's datagram only once it is admitted and for every reply, as on the public UDP relay, drops what is over the rate, and follows a service's clients with the same failover as TCP (D25).
  - The visitor closes the channel once its peers have expired, and the server closes a visit with no datagram either way for `udp.session_timeout_secs`. An idle visitor keeps no server state (D22).
  - A reload closes a visit that is no longer granted, and a UDP service visit whose target changed. TCP connections keep running in that case; the next datagram opens a new UDP visit to the new target.
  - The socket-to-channel loop is shared with public UDP services (`src/udp/front.rs`).
- **Protocol is explicit.** A forward has `protocol: tcp|udp`, like a service, and is never inferred. The visitor binds before it talks to the server, and a wrong guess would bind the wrong socket. A mismatch is answered `4 invalid`, and `burrow visit` asks for the grants to say which protocol to set. A server older than v0.1.2 answers `4 invalid` to the UDP flag and to `0x21 0x01` (checked against v0.1.1). `init visitor` then falls back to TCP-only grants and keeps existing UDP forwards. A v0.1.2 server whose grants do not fit in one answer gives the same `4 invalid`, so the message names both causes.
- **`reach` stays address-only and covers TCP and UDP**, like a client's `allow` list and a service's `allow_from`. A `reach` grant gives the same addresses and ports over both protocols, so an existing grant now also allows UDP to them; the client's `allow` list still has the final say. A per-protocol rule or an opt-in flag would add config for little gain: `reach: any` already gives arbitrary TCP. `validate` says "over TCP or UDP" in its `reach: any` warning.
- **`self`** follows D38 for UDP through the same gate: the server's own TCP listen, WebSocket and metrics ports stay TCP-only refusals, and link-local and metadata addresses need `self.allow` to name them. A `unix:` target is refused for UDP (`4 invalid`) before any client sees it.
- **Limits and timers:**
  - `udp.session_timeout_secs` now defaults to 120 s on the server, client and visitor (was 60 s). RFC 4787 section 4.3, REQ-5, says a NAT UDP mapping "MUST NOT expire in less than two minutes", except for some well-known ports, and recommends five minutes or more (REQ-5c). RFC 4787 is updated by RFC 6888 and RFC 7857, and neither changes REQ-5. The cost is that peers that change source port per request, such as DNS, are held longer: at the default `max_udp_peers` 8192, a client drops new peers above about 68 such queries per second, instead of 136. The value stays configurable.
  - Mappings are refreshed by outbound traffic, which REQ-6 requires.
  - Following RFC 8085, datagrams are never fragmented or queued without bound. The largest datagram is 65515 bytes and larger ones are dropped with a debug line. Over-rate datagrams are dropped, not delayed. Every queue is bounded: per channel, per SOCKS destination, and 1 MiB per SOCKS association.
  - A UDP visit counts as one connection of the visitor and of the client. The service's `max_connections` stays TCP-only.
- **Spoofed sources:** a UDP forward or SOCKS relay listening off loopback accepts any source address, as UDP has no handshake, so a forged one can fill `udp.max_peers` and send replies elsewhere. docs/visitors.md says to keep `local` on 127.0.0.1 unless the network is trusted. Popular tools accept the same risk for UDP listeners.
- **SOCKS5 UDP ASSOCIATE** follows RFC 1928:
  - §4 and §6: the relay port is bound on the address the app connected to, made plain IPv4 when the forward listens on a dual-stack `[::]`. The reply gives that relay address in BND.ADDR and BND.PORT. A v4-mapped address cannot be used by an IPv4 app, and fails where IPv6 sockets are IPv6-only by default: Windows sets IPV6_V6ONLY by default (Microsoft Learn, "Dual-Stack Sockets"), and FreeBSD has `net.inet6.ip6.v6only` on by default (inet6(4)).
  - §7: datagrams from any source other than the app are dropped. The relay admits the IP address of the app's TCP connection only, and an address named in the request on another host is ignored, so the relay cannot be aimed at a third party. A port named in the request must match; otherwise the first sender's port is locked in.
  - §7: fragmentation is optional, and an implementation without it MUST drop FRAG not 0, so it is dropped with a debug line.
  - Replies carry the header the app sent, so a host name stays a host name; the client resolves names (D28).
  - Each destination gets its own visit (kind 2), so the client stays unchanged and `reach` and `allow` decide per destination. There are at most 64 destinations and 1 MiB of waiting datagrams per association.
  - The association ends when its TCP connection closes (§6), and also after `udp.session_timeout_secs` with no datagram.
  - Header parsing is strict (reserved bytes 0, ATYP 1, 3 or 4, exact lengths, a valid host:port, port not 0) and has its own fuzz target, `socks_udp_header`.
- **No SOCKS crate:**
  - `socks5-proto` (0.4.1) and `socks5-impl` (0.10.3) are GPL-3.0-or-later, which our MIT licence and deny.toml exclude.
  - `socksv5` (0.3.1) has had no release since 2022-12-08.
  - `fast-socks5` (1.0.0, MIT, maintained) would replace only about 40 lines of UDP header parsing. It would also add a second socket2 (0.5) and a typestate server that does not fit our refusal handling.
  - So burrow keeps its own strict, fuzzed parser, as it did for CONNECT. This should be revisited if fast-socks5 offers standalone parsers that do not need its server.
  - Sources: crates.io and docs.rs pages of each crate, checked 2026-10-23.

## D43. Websites on one HTTPS port: the web: block, one crate, one seam, nothing hidden

burrow can put several TLS services and, later, websites on one HTTPS port of the server, told apart by name, and the WebSocket tunnel can share that port (docs/web.md). The shape:

- **Off unless written.** Nothing listens unless the top-level `web:` names `https`, `http` or both. A service becomes a website by having its own `web:`; a service `web:` without the top-level block, or in a build without the `web` Cargo feature, is a validate error, so a key never does nothing. The tunnel shares a port only when `websocket.listen` is written the same way as `web.https` or `web.http` (both a bare port, or the same ip:port; a mix is an error) and `websocket.host` names it. `burrow validate` (text and `--json`), `burrow status` and the admin overview show the same summary, built by one function from the settings.
- **One word, `web`.** The config key, the Cargo feature, `src/server/web.rs` and the crate `burrow-web` use it. The service block (`web: name`, `web: [a, b]` or `{hosts, tls}`) keeps the tunnel part of the service unchanged: clients, `self`, failover, health checks, `allow_from`, `max_connections`, `bandwidth` and `proxy_protocol` work for websites as for a TCP service, because a website connection is a normal service visit.
- **The crate.** `crates/burrow-web` holds the listener, the TLS name peek, the PROXY header reader, the name table, the pre-TLS limits and the tunnel hand-off. It never depends on `burrow`, `burrow-config` or the admin and UI crates, and they never depend on it (`cargo xtask arch-check`), so the WebAssembly UI does not grow.
- **The seam.** `Upstream::open(service, &Visitor { addr, local, host })` returns one boxed stream (`Box<dyn Io>`). It differs from the design sketch in three ways: it carries the local address, so the PROXY header to the app names the real HTTPS port; it hands the tunnel over with `tunnel_permit(peer)` and `tunnel(TunnelConn)`, so a tunnel connection moves from the web pool of pre-TLS slots to the tunnel's own `max_handshakes` pool before TLS starts and the two pools cannot starve each other; and `open` refuses up front only what is known before a client answers (`allow_from`, `max_connections`, no client). The root crate implements it with an in-memory pipe and the existing `visit()`, now generic over `Split`. A pipe end carries a reset flag, because a dropped tokio `DuplexStream` reads as a clean end of stream (tokio docs, `DuplexStream`), and a target that resets must reach the browser as a reset.
- **Reading the name.** The first TLS message is read with rustls' `Acceptor` fed with copies of the bytes, and the bytes are then replayed to the app or to the TLS acceptor. Limits: 10 seconds, 16 KiB plus a record header, the first byte must be a TLS handshake record (0x16), a hello split over several records is read whole, and any Acceptor error closes the connection without an answer. The name is compared without case and without a final dot (RFC 6066 section 3, which also forbids IP literals in the name). A connection without a name reaches the site of the address it connected to, if one lists it. An unknown name is closed without a certificate. A wildcard covers exactly one label (RFC 6125 section 6.4.3, now RFC 9525 section 6.3).
- **PROXY headers from a load balancer** are parsed by `ppp`. A v1 line has at most 107 bytes (HAProxy specification). A v2 header is 16 bytes plus the 16-bit length in its 15th and 16th bytes, and its TLVs have no total limit. The specification only designs both versions to fit in one minimal TCP segment of 536 bytes, and a sender that sets every TLV it defines can pass that: an authority (a TLS name of up to 255 bytes), a unique ID of up to 128 bytes, the SSL TLV with its client certificate name and cipher, and CRC32C. Cloud balancers add little: AWS PrivateLink's VPC endpoint ID (type 0xEA), Google Private Service Connect's 8-byte connection ID (type 0xE0) and Azure Private Link's LinkID (type 0xEE). So burrow reads the length first and refuses a header over 2048 bytes before reading its body: more than twice the largest real header, and under nginx's 4096-byte cap (`NGX_PROXY_PROTOCOL_MAX_HEADER`). LOCAL and UNKNOWN keep the real peer; bytes after the header are kept. The reader and its fuzz target exist now; `web.proxy_protocol_from` turns it on with the rest of P3.
- **The tunnel by path.** On a name that a site shares with the tunnel, burrow answers the WebSocket upgrade on the tunnel's path itself and hands the upgraded stream to the same WebSocket code (`ws::serve_upgraded`), with the same message, control-frame and keepalive limits. tokio-websockets 0.13.3 keeps its request parser private (`upgrade::client_request` is `pub(crate)`), so the accept key is computed in one small function with aws-lc-rs's SHA-1 and base64 as RFC 6455 section 4.2.2 says, tested with section 1.3's example; another version than 13 gets 426 with `Sec-WebSocket-Version: 13`. One `limits.handshake_timeout_secs` covers TLS, the upgrade and burrow's handshake together.
- **Dual stack.** A bare `web.https` port binds `[::]` with `IPV6_V6ONLY` cleared explicitly, through the same `bind_tcp` as every listener, because the default differs: Linux follows `net.ipv6.bindv6only` (0 by default), Windows sockets are IPv6-only by default (Microsoft Learn, "Dual-Stack Sockets"), and FreeBSD has `net.inet6.ip6.v6only` on by default (inet6(4)).
- **Final forms first.** A site's `tls` is `auto` (the default with `web.https`), `passthrough`, `off` (the default without it) or `{cert, key}`, and `web.https` is optional (`web:` needs a port). The keys were written in their final form from the start, and each phase lifted a refusal instead of changing the config. Since P2, burrow terminates HTTPS itself (D44) with its own files or Let's Encrypt (D45), serves plain HTTP on `web.http`, and validate refuses only what cannot work, each with the fix: a name with no certificate source or no possible Let's Encrypt check, a plain site without `web.http`, a redirect choice the site's form cannot honour. The tunnel's own name takes `websocket.tls`, then a `web.certificates` entry, then Let's Encrypt; on `web.http` it needs no certificate.
- **What the admin UI may change.** The web proxy itself is editable in `burrow admin`, except what reads files: `web.letsencrypt.ca`, the `cert` and `key` of each `web.certificates` entry and of a site's own `tls: {cert, key}` (config.md section 6). **Owner decision 0x:** `web.https` and `web.http` are no longer locked, like a service's public `bind`; a write admin may set, change or remove them, and the New website flow turns the web proxy on with its ports. Guards: a port shared with the tunnel (`websocket.listen` written the same way) is refused, since moving it disconnects every client; each new web address is test-bound before the file is written, so a port in use or without permission refuses the plan with the reason; and Review shows "opens port N" for a new or changed port and which websites stop when one is removed. **Owner decision 0y:** the `websocket` block is no longer locked either: a write admin may turn it on (the new listener is test-bound first, like a web port), change `listen`, `path`, `host`, `keepalive_secs` and `challenge`, or turn it off; its `tls` files stay locked. A session that arrives over the WebSocket listener cannot move it or turn it off (the self-transport guard), and Review warns with the names of the clients connected over WebSocket now, which are cut off and need their own config changed; a new `host` names the clients that use it. A lock can now name entries of a map or list with a `*` segment (`services.*.web.tls.cert`), and a plan from the admin channel is refused when it would set or change any locked value, whatever path the change takes (a field, its parent, the whole service, raw text, a new service); removing an entry that holds one is allowed, and a revert keeps the current locked values. Top-level locked values may not be removed either; turning the web proxy off from the admin UI works when none of its locked values (files) is set.

## D44. HTTPS termination: one peek, one shared config, Host equals the TLS name

burrow ends TLS itself for a site whose `tls` is `auto` or `{cert, key}` and speaks HTTP/1.1 to the browser with hyper, then sends each request to the site's service through the same `Upstream::open` seam as passthrough (D43). The shape:

- **The peek decides.** Every connection on `web.https` is read up to the end of its TLS hello first (D43). The name picks one of four ways: passthrough replays the hello to the app; the tunnel's own name hands the stream to the tunnel; a name whose site only holds the tunnel by path goes to the tunnel's HTTP code; a terminated or plain site gets burrow's TLS. The bytes already read are replayed into rustls through `Prefixed`, so the peek costs no second read and the hello is parsed by rustls itself, not by burrow.
- **One shared server config.** All terminated names share one `ServerConfig` built once with `with_cert_resolver(Certificates)`, so a new or renewed certificate is used by the next handshake without rebuilding anything, and open connections keep the session they have (a test swaps a site's file on reload and keeps an open connection working). ALPN offers only `http/1.1`: a hello that offers protocols and none of them overlaps is refused by rustls with `no_application_protocol`, as RFC 7301 section 3.2 says, and a hello without ALPN proceeds. HTTP/2 is not offered yet. The provider is rustls' aws-lc-rs with its safe default versions (TLS 1.2 and 1.3) and X25519MLKEM768 preferred (D55).
- **Per-connection configs only where needed.** A hello without a name that reaches an IP site (RFC 6066 section 3 forbids IP literals in SNI, so browsers send none) gets a config holding that site's one certificate, because the resolver is keyed by name. A hello that offers exactly `[acme-tls/1]` for a name with a pending TLS-ALPN-01 challenge gets a one-shot config with the challenge certificate and ALPN `acme-tls/1` only; after the handshake burrow closes the connection, since the protocol carries no application data (RFC 8737 sections 3 and 4). `acme-tls/1` is never in the shared config, so a visitor can never negotiate it, and a hello that offers it beside `http/1.1` gets `http/1.1`. A passthrough name without a challenge gets its hello to its app unchanged, `acme-tls/1` included.
- **Host must equal the TLS name.** The request's host is the one `Host` field, or the authority of an absolute-form target, which wins (RFC 9112 section 3.2.2), lowercased, without port or final dot, an IPv4-mapped IPv6 address in its IPv4 form. A request without a Host, with two, or with one that is not a valid authority (userinfo included) gets 400 (RFC 9112 section 3.2). On a TLS connection a host other than the name of the hello gets 421 Misdirected Request (RFC 9110 sections 7.4 and 15.5.20), because the certificate only proves that name and RFC 6066 section 11.1 makes a server that relies on the names being equal check it. This also stops a browser's connection reuse from carrying a request to another site. CONNECT gets 400.
- **Every limit explicit.** hyper's http1 server runs with `header_read_timeout` = `web.request_header_timeout_secs` (10 s; since hyper 1.6 the same timer also runs while a kept-alive connection waits for its next request, hyperium/hyper#3828), `max_header_size` 32 KiB and `max_headers` 100 (both answer 431 and close), `keep_alive` on and `half_close` off. hyper itself refuses the smuggling shapes: Content-Length with Transfer-Encoding is read as chunked with the length dropped, two different lengths and an unknown transfer coding are 400 and close, and an obs-fold is 400 (RFC 9112 sections 5.2, 6.3 and 11.2); tests send each one and check that nothing hidden in a body reaches the app.
- **The idle rule.** A connection is closed when for `web.idle_timeout_secs` (60 s) no byte has moved either way and no request is in flight. A wrapper around the stream stamps the last byte and the service counts requests in flight, with one timer per connection. A slow app that is still working on an answer is never cut by it (`response_header` covers that, 504 after 60 s), and an upgraded connection such as a WebSocket is never idle-closed: once joined, it belongs to the two ends.
- **The upstream.** One hyper client stream per browser connection and service, opened through `Upstream::open` and reused for the next request when it is ready within a second. Hop-by-hop fields are removed both ways: those named in Connection, and Connection, Keep-Alive, Proxy-Connection, TE, Trailer, Transfer-Encoding and Upgrade (RFC 9110 section 7.6.1). X-Forwarded-For and X-Real-IP are set to the visitor's address, replacing what the browser sent (trusted proxies come later), with X-Forwarded-Proto, X-Forwarded-Host and X-Forwarded-Port. Host passes unchanged; an absolute-form target becomes origin-form with Host set to its authority. A 101 from the app joins the two upgraded streams.
- **Pages before the first byte, resets after.** A refusal known before the app answers is a short built-in page on a connection that stays usable: no client or a client down 503, a client at its limit 503 with `Retry-After: 10`, not allowed 403, a denied or unreachable target 502, an app that resets before answering 502, no answer in time 504. Once the app's answer has started, a failure resets the browser's connection, as passthrough, the tunnel and plain TCP services do, so a cut-off body is never mistaken for a whole one. Pages exist for 400, 403, 404, 413, 421, 429, 502, 503, 504, the certificate-pending 503 and maintenance.
- **The drain.** On stop or when the web proxy is turned off, each connection gets hyper's `graceful_shutdown`: a request in flight finishes and is answered with `Connection: close`, idle kept-alive connections close at once, and after 10 seconds whatever is left is dropped.
- **Port 80 (`web.http`).** Plain HTTP goes through the same pipeline, without the 421 rule (there is no TLS name). In order: `/.well-known/acme-challenge/<token>` with a base64url token is answered from the ACME manager as `application/octet-stream` before any routing (RFC 8555 section 8.3); then the tunnel, when it shares this port (below); a `tls: off` site and an HTTPS site with `https_redirect: false` reach their app with `X-Forwarded-Proto: http`; other HTTPS sites get 308 Permanent Redirect to the same path on `https://` (RFC 9110 section 15.4.9 keeps the method and body), naming the port when it is not 443, or the pending page while their certificate is pending or failing, so a browser is never sent to a certificate error; passthrough, tunnel-only and unknown names get 404.
- **`web.https` optional.** Without it nothing listens on an HTTPS port and every site must be `tls: off` (decision 0b); a single-label name such as `nas` is allowed only on such sites (decision 0f).
- **The tunnel by path.** When `websocket.host` is a terminated site's name, the tunnel takes its path on that site's connections with the site's certificate from the shared resolver; validate refuses it on passthrough sites, on `tls: off` sites when it shares the HTTPS port, and on the path `/`.
- **The tunnel on port 80 (decision 0h).** When validate finds `websocket.listen` equal to `web.http` (`shares: Http`), the root sets `TunnelSettings.port` to `Http` and the tunnel rides that port over plain `ws://`, still encrypted end to end by burrow's own Noise layer. Each request on :80 is checked in order: the ACME HTTP check, then the tunnel, then `https_redirect` and the sites, so a redirect never catches the tunnel. On its own name the tunnel owns the whole name as on 443 (the WebSocket upgrade on its path is handed over, a plain request on the path gets 426, any other path 404); on a site's name, HTTPS or `tls: off`, it takes its path and below and the site keeps the rest. The upgrade goes through the same `tunnel::answer` and hand-off as the tunnel by path on 443 (RFC 6455 section 4.2.2). The tunnel then rides only that port: its name is closed on the HTTPS port, and it asks for no certificate.
- **Any port.** Sharing depends on `websocket.listen` being the same address as `web.https` or `web.http`, never on the number 443 or 80: the runtime has no port number in its rules other than leaving `:443` out of a redirect's address. The tests run on random high ports.
- **No sites.** A `web:` block without sites runs: on HTTPS every name other than the tunnel's is closed before TLS, on port 80 it gets 404, and the tunnel's own name gets its certificate through the shared resolver like a site (`websocket.tls`, a shared file, then Let's Encrypt). Which certificate a name gets, and which checks and wildcards are allowed, is config.md section 3.15's one set of rules (D45); termination only asks the resolver.
- **Written here, after looking for a library.** The idle wrapper: tokio-io-timeout 1.2.1 only has per-direction read and write timeouts that start when one operation waits, so it would cut a kept-alive connection whose request a slow app is still answering, and cannot see requests in flight; the idle rule needs both directions and the in-flight count, so it is one small wrapper and a counter. The :80 redirect: tower-http 0.7.1 `services::Redirect` sends every request to one fixed URI and brings the tower Service stack that crates.md turned down, while this redirect keeps each request's host and path, names a port other than 443, and comes after the ACME check, the tunnel and the pending page, so it is one function, `https_location`. The error pages: hyper and tower-http have no status pages (tower-http's `set_status` only changes the code), and the pages are fixed short texts, so they are one `Page` enum with each status and body.

## D45. Certificates: own files, then Let's Encrypt, kept in a state folder of their own

burrow terminates HTTPS with a certificate per name, chosen in one order (config.md 3.9): the site's own `tls: {cert, key}`, then a `web.certificates` entry whose `hosts` lists the name, then `web.letsencrypt`, else validate refuses the name. A listed wildcard covers one label (RFC 9525 section 6.3); validate and the server pick the entry with the same function, `burrow_syntax::web::entry_for`, so they cannot drift. The tunnel's own name takes `websocket.tls` first.

- **Files.** PEM is read with rustls-pki-types `PemObject` (rustls-pemfile is unmaintained, RUSTSEC-2025-0134). The key is checked against the leaf with `CertifiedKey::from_der` and then `keys_match()` explicitly, because `from_der` accepts an unknown key match. A file must cover each name it is used for, checked by rustls-webpki (`verify_is_valid_for_subject_name`, the browsers' rules; a listed wildcard must be in the file as that wildcard). Dates come from x509-cert with its `Raw` profile, so a file rustls accepts is never refused for its dates; a warning comes 14 days before expiry. Files are read on a blocking thread, never on the async workers, and every file path is watched by the reload watcher; the settings hold a digest of the files' bytes, so a certificate rewritten at the same path (certbot's `live/` links) is applied on the next reload. A file that breaks keeps the last good certificate in use.
- **Let's Encrypt is opt-in.** Only `web.letsencrypt: {email}` turns it on, and writing it accepts the CA's terms. Let's Encrypt stopped sending expiry mails on 2025-06-04 and no longer stores contact addresses; the email stays required as the deliberate act and is sent, because other ACME servers use it. `burrow status`, the metrics `burrow_certificate_expiry_timestamp_seconds` and `burrow_certificate_failures_total` and the admin UI show what the mails used to say.
- **instant-acme 0.8.5, pinned,** with `aws-lc-rs` (the same provider as all of burrow's TLS, D55), `rcgen` and `time`, without hyper-rustls or x509-parser, through our own HTTP client on hyper and tokio-rustls. The client talks HTTPS only, follows no redirects, has a 10-second connect and a 60-second request limit and a 1 MiB answer cap, trusts webpki-roots plus `letsencrypt.ca`, and keeps instant-acme's User-Agent (Pebble requires one). It clamps `Retry-After` to 30 days before instant-acme reads it, because 0.8.5 adds the seconds to `SystemTime::now()` without a check (`lib.rs`, `retry_after`) and a hostile server could make burrow panic, and it records the `Retry-After` of a 429 or 503, which 0.8.5 drops from `rateLimited` problems. A hand-written client instead of hyper-rustls: hyper-rustls would bring a second client stack (hyper-util's legacy pool and tower) for six requests an order.
- **The account** is one per directory URL, in `<state>/acme/<hash of the URL>/`. Its key is written (0600) before the account is created, and the account is created from that key, so a crash or a failed write between "created" and "saved" finds the same account again instead of making a second one (Let's Encrypt allows 10 new accounts per IP address every 3 hours). Status and validate show the account URL for a CAA `accounturi` record (RFC 8657); validate reads it from the state folder offline, and says so in one line when it cannot read the folder.
- **Orders.** One certificate per service for all its names, one order at a time on the server, TLS-ALPN-01 first (RFC 8737; its certificate carries the critical acmeIdentifier extension and is served only to a hello that offers exactly `acme-tls/1`), HTTP-01 on `web.http` next (RFC 8555 section 8.3), both answered before any site rule. An IP address is an `ip` identifier (RFC 8738) answered on its reverse name and ordered with the `shortlived` profile when the directory lists it; `letsencrypt.profile` is used for names only when the directory lists it, otherwise status says which profiles it offers and no order is made. Names are read from the SAN only. A new chain is used only after it parses, its key matches and it covers every name; it is written atomically to `<state>/certs/<first name>-<hash of the sorted names>/` (0700 folders, 0600 files) before it is served, and stored certificates are served at start before any network call.
- **No duplicate certificates (owner decision 0i).** Certificates are kept by their names, not by the service that ordered them. Any stored certificate from the same directory that covers all of a service's names is served, whoever ordered it, so a restart, a reload, a renamed service or a name moved to another service orders nothing; before any order, a stored certificate that covers the names and is not yet due for renewal (two thirds of its life) is used instead. The tunnel by path on a site's name adds no name of its own and uses the site's certificate. A certificate no service uses stays 30 days, so adding the name back costs no order. A guard allows at most 4 new certificates per exact set of names in 7 days, counted in `<state>/acme/<directory>/issued.json` so a restart cannot reset it; a fifth waits, and status says until when. Let's Encrypt allows 5 certificates per exact set of identifiers every 7 days, with no override, and exempts ARI renewals (an order with `replaces` for a certificate not yet replaced) from all limits, so renewals with `replaces` are not counted; one left over is for a manual order or a crash between issuing and saving.
- **Name changes (owner decision 0l, config.md 3.15 rule 6).** A name on a new service gets its own order. A name added to an existing service re-orders that service's certificate for all its names, sent with `replaces` for the old one (they share a name, so it counts as an ARI renewal); the old certificate keeps serving the names it covers, and the new name answers with the pending page until its certificate arrives. A removed name orders nothing: the certificate that covered it keeps serving the others until its next renewal, which then orders the smaller set. Orders run one at a time on the server, and status lists the queue (`acme.queue`: service, names, when, and which one runs). A stored or reused certificate that covers the names still wins over any of these orders.
- **One rule for each name's check (owner decision 0j, config.md 3.15 rule 1).** validate and the runtime both call `burrow_syntax::web::checks_for`: DNS-01 for a wildcard or `challenge: dns` (never for an IP address), otherwise TLS-ALPN-01 when `web.https` is port 443 and HTTP-01 when `web.http` is port 80, because the CA connects only to those ports (RFC 8737, RFC 8555 section 8.3; a router may forward them to other local ports). An order tries TLS first, then HTTP, within the checks every one of its names allows. A name with no possible check is never ordered; status gives the reason, and a stored valid certificate that covers it is still served. Each name gets its own check, so a certificate with a wildcard and other names checks the wildcard over DNS and the others over TLS or HTTP (D48). A name needing DNS takes the letsencrypt.dns entry whose domain covers it most specifically (burrow_syntax::web::dns_entry_for, shared by validate and the runtime); a name under a listed shared wildcard needs no check of its own.
- **Learning and hints (owner decisions 0o and 0p, config.md 3.15 rules 1, 8 and 10).** A site's `challenge` or `websocket.challenge` (`tls`, `http`, or `dns` from P6) makes that the only check tried for its names, through the same `checks_for` as validate; by path the tunnel follows its site's. Unless one is set, burrow tries TLS first (it needs no extra port and works where an ISP blocks port 80), then HTTP, and remembers per name the check that last worked (`<state>/acme/<directory>/checks.json`), trying it first next time, as Caddy does, so a name behind a CDN does not fail the TLS check on every renewal and spend Let's Encrypt's failed-validation allowance. A failed check shows the CA's text with a hint, chosen by the ACME problem type (RFC 8555 section 6.7) and by the text only when the CA gives no type: a `tls` problem, typically Cloudflare's `Cannot negotiate ALPN protocol "acme-tls/1"`, means something in front answers HTTPS ("open http: 80 and use challenge: http, or use challenge: dns"); a `connection` or `dns` problem means the name may not be reachable from the internet ("for internal names use challenge: dns"). After a TLS failure, HTTP-01 follows at once when port 80 is open; otherwise the normal backoff and, for Let's Encrypt production, the staging fallback apply, so the rate limits stay safe. The old certificate keeps serving and other names are unaffected.
- **Renewal** follows ARI (RFC 9773): a random time in the suggested window, the next check after `Retry-After` clamped to 1 minute to 12 hours (Let's Encrypt asks for at least two checks a day), 6 hours after an answer that is not usable; `replaces` is sent while the old certificate is unexpired; it is dropped at once after a 409 `alreadyReplaced`, and on the third try after two other refusals of the order (D58). Without ARI, renewal comes at two thirds of the life, or half for certificates under 10 days (Let's Encrypt integration guide). The ARI id is built from x509-cert's AKI and serial and tested against RFC 9773's example.
- **Failures back off like Let's Encrypt asks:** 1 minute, 10 minutes, 100 minutes, then daily, plus up to a tenth of jitter, never sooner than a `Retry-After`. Every 6 hours would pause a forgotten broken name after about 384 days (1,152 consecutive failures, refilled one a day). Short-lived certificates retry at most every 6 hours while more than 2 days are left, then every 15 minutes to 4 hours, below the 5 failed authorizations per hour per name. An error is logged with under 7 days left (2 for short-lived). A failure never closes a listener or touches another service, and the old certificate is served even after it expires.
- **The staging fallback** is used only for Let's Encrypt production: after a failure, one order goes to the staging service in the gap before the next production try, and its result is a note in status ("the test service accepted the same checks"). Production keeps its own schedule; a staging success can bring the next production try forward to 100 minutes after the failure at the earliest, never sooner. A test certificate is never served. This avoids two traps of "staging until it works, then production once": a CAA `accounturi` pinned to the production account fails every staging try, and production must not fail at staging's pace.
- **The state folder** exists for every server with `web:` (an installed service gets it at install, so uploads and the local CA work when added later) and is made on first write. It holds the ACME account and certificates, the local CA's keys and the uploaded files. `burrow server --state-dir DIR` names it; an installed server service passes it, a command given the service's installed config (`/etc/burrow/<name>/server.yaml`) uses the service's folder, and otherwise a server run by hand uses one folder per config file under the user's state folder (`dirs::state_dir()/burrow/servers/<file>-<hash>`), also for the source config a service was installed from, so a hand run never writes into or prunes a running service's folder. Unused uploads are pruned at start and on reload only in a folder named by `--state-dir` or one that is no installed service's, and an upload that any version in the admin history (`.server.yaml.history/`) still names is kept, so after a reinstall from the source config a revert from Activity still finds its files. The history is scanned as text for upload names rather than loaded, since an old version may no longer pass validate; a stray match only keeps a file longer. `burrow status` (and its JSON, `acme.state_dir`) names it. An installed server service with `web:` gets its folder from the system: systemd `StateDirectory=burrow/<name>` with `StateDirectoryMode=0700` (systemd.exec(5): owned by `User=`, writable under `ProtectSystem=strict`, not removed when the unit stops; not under `/run`, which is cleared at boot), launchd has no such key (launchd.plist(5)), so the installer makes `/Library/Application Support/burrow/<name>` 0700 for the service account, and on Windows `%ProgramData%\burrow\services\<name>` (the service's config folder is `%ProgramData%\burrow\<name>`) owned by Administrators, with inheritance removed and only SYSTEM, Administrators and the service account (Modify) on it (icacls). Uninstall keeps the folder like the config folder and prints where it is and how to delete it; only `--purge` deletes it. `--purge` never deletes a file or folder another installed service owns (its config, env file, log and its rotations, web access log or state folder), and says which it kept: on Windows the services share one log folder, so `<name>-access.log` can also be the log of a service named `<name>-access`. Deleting it on every uninstall would lose the account and every certificate, and a reinstall would order them all again against the limit of 5 certificates per exact set of names every 7 days.
- **No dns-persist-01 in v0.2.0.** It is still an IETF draft, and Let's Encrypt had not shipped it in production as of 2026-10-24 (announced 2026-02-18 at https://letsencrypt.org/2026/02/18/dns-persist-01/; the timeline is tracked at https://community.letsencrypt.org/t/dns-persist-01-deployment-status-and-timeline/246468). `challenge` takes `dns`, `http` and `tls` only.
- **Accepted risks** (industry standard): HTTP-01 over plain port 80; validation from several Let's Encrypt vantage points means a firewall that allowlists or geo-blocks breaks it; no HTTP proxy for ACME (instant-acme issue 297 is open too); if Let's Encrypt drops the X1/X2 cross-signs before webpki-roots ships the Gen Y roots, `letsencrypt.ca` is the workaround. An admin with write access can set `letsencrypt.directory` to any HTTPS URL, so the server sends HTTPS requests there, outside `self.allow` and D38's gate; only `letsencrypt.ca` is locked, because write admins are trusted with the config (D39).

## D46. Handing the state folder over: by descriptor, never through a hard link

Install gives a launchd service's state folder to its account, and uninstall without `--purge` gives it back to root; the account controls what is inside. The walk opens each folder with `O_DIRECTORY|O_NOFOLLOW` and works relative to that descriptor (rustix `openat`, `statat` with `AT_SYMLINK_NOFOLLOW`), so a folder swapped for a link mid-walk is never followed. A file is opened with `O_NOFOLLOW` and changed with `fchown` only when `fstat` shows a regular file with one link; a file with more links is left alone and named in the output, because changing it would change the linked file too (a root-owned plist linked in by the account would become the account's). Links themselves and other file types are left as they are. This is the rule systemd-tmpfiles adopted for CVE-2017-18078 (v237: fstat the opened file and refuse `st_nlink > 1`); macOS has no `protected_hardlinks`, and Linux has it only when the sysctl sets it. burrow writes by temporary file and rename, so its own files always have one link. Accepted: a service-account process that escaped the stop (setsid) could delete its planted link between the open and the nlink check; systemd-tmpfiles accepts the same race in its CVE-2017-18078 fix.

## D47. Request paths: cleaned once, matched on segment boundaries; forwarded headers only from trusted proxies

Every request path is normalized once, at the top of the pipeline, and the result is what the tunnel-by-path check, redirects, routes and the app all see; only the ACME token check reads the raw path, since its token alphabet is strict. Escapes of unreserved characters are decoded and every other escape is written in upper case (RFC 3986 section 6.2.2), so `/%61pi` is `/api` and `%2f` routes like `%2F` (Caddy CVE-2026-27587 was a case bug in escape matching). A reserved escape is not its character (RFC 3986 section 2.2): `%2F` stays data, so GitLab's `group%2Fproject` reaches the app unchanged, as in Traefik since 3.4.1. Bytes above ASCII and `"` are percent-encoded, so `/é` and `/%C3%A9` route the same and a redirect's Location is always ASCII. Repeated slashes are merged before matching and the merged path is what the app gets: matched like nginx (`merge_slashes`), forwarded cleaned like Traefik (`sanitizePath`) and Envoy (`merge_slashes`). `.` and `..` segments are refused with 400 instead of removed, also when encoded and when `%2F` or `%5C` would make one (`/public%2F..%2Fadmin`, Envoy CVE-2021-29492, Traefik CVE-2025-32431); browsers resolve dot segments before sending, so only crafted requests carry them. A raw `\`, `%00` and a broken escape are refused too.

A route's path matches on segment boundaries: `/api` takes `/api` and `/api/...`, never `/apix` or `/api..` (the nginx alias off-by-slash class). That is stricter than Traefik's `PathPrefix`, which is a plain string prefix. Routes are chosen on a match view of the path in which `%2F` and `%5C` count as `/` and each segment's `;parameters` are ignored, while the app still gets the path with `%2F` and `;` as sent (owner, 0v): an app that decodes `%2F` or drops path parameters before routing, as Tomcat, Spring and many PHP setups do, cannot be reached at `/admin%2F` or `/admin;x=1` past a route on `/admin` (Traefik CVE-2025-66490, Shiro CVE-2020-1957, Spring Security's StrictHttpFirewall). A segment that is `.` or `..` before its `;` (`/..;/admin`) is refused with 400. Paths match without regard to ASCII letter case (owner, 0v), like Caddy's path matcher, because IIS, ASP.NET and macOS or Windows file systems serve `/ADMIN` as `/admin`; the app still gets the case that was sent, and validate refuses two `paths` that differ only by case. Configured paths go through the same normalizer, so validate and the proxy agree. No library fits: `fluent-uri` removes dot segments and does not merge slashes, `url` follows WHATWG and decodes `%2e%2e` as `..`, and none refuses dot segments or keeps reserved escapes in one canonical form, so `burrow_syntax::url_path` is hand-written, small and fuzzed (`path_normalize`).

Accepted risk: merging slashes changes paths that carry data with `//` (an S3-style key, a URL inside a path). Envoy notes that merging is not part of the HTTP specification, and nginx, Traefik and Envoy merge by default all the same.

A visitor's own `Forwarded`, `X-Forwarded-*`, `X-Scheme`, `X-Real-IP` and `X-Request-Id` never reach the app, and neither does any header that reads as one of those with `_` for `-`, from anyone (Spring's "Forwarded Headers" security note asks an edge proxy to remove both `Forwarded` and `X-Forwarded-*`; nginx drops underscored names by default; Traefik's forwardedheaders middleware). Names listed in `Connection` are removed first, but never `Host` or a header burrow sets (Traefik CVE-2024-45410, Apache CVE-2022-31813). Behind `trusted_proxies`, `X-Forwarded-For` is read right to left and the first untrusted entry is the visitor (nginx `real_ip_recursive`, Caddy `trusted_proxies_strict`); an entry that does not parse stops the walk at the last trusted hop. The visitor found that way is what `allow_from`, the PROXY header to the app and the access log use, and an app connection is reused only for the same visitor. `X-Forwarded-Port` follows Traefik: a trusted proxy's own value, else the port in `Host`, else 443 for HTTPS and 80 for HTTP, so an app behind Cloudflare on port 80 does not build `https://host:80/`. On port 80, `https_redirect: true` answers 308 unless a trusted proxy says `X-Forwarded-Proto: https`: a `tls: off` site behind a proxy redirects by that header (ingress-nginx `force-ssl-redirect`), and an HTTPS site reached over plain HTTP from a proxy that already speaks HTTPS to the visitor is served, so a proxy in Cloudflare's "Flexible" mode does not loop. A site with `client_auth` is the exception: its names always redirect on port 80, whatever `https_redirect` or a proxy says, and validate refuses `client_auth` with `https_redirect: false`, because the device check lives only in burrow's own TLS handshake (D49).

Accepted risks, written by the owner of each site: `compress: true` makes a page that reflects a secret next to visitor input open to BREACH-style length guessing over HTTPS, the risk every proxy's gzip option carries (nginx `gzip`, Caddy `encode`, Traefik `compress`); compression is off by default, only for text-like types, and never for `Cache-Control: no-transform`. `target_tls: {insecure_skip_verify: true}` sends a site's traffic to an app whose certificate is not checked, so anyone on the path to the app can read it; the key name says so, validate prints a note naming the site, and the handshake signatures are still verified, as in Go's `InsecureSkipVerify` and Traefik's `insecureSkipVerify`.

Sources, checked 2026-10-25: RFC 3986 sections 2.2, 2.3, 6.2.2; RFC 9110 sections 4.2.3, 7.6.1; RFC 7239 section 8.1; nginx `ngx_http_core_module` (`merge_slashes`), `ngx_http_proxy_module` (`proxy_pass`), `ngx_http_realip_module`; Traefik "Request path" security page (v3.6) and the forwardedheaders middleware source; Envoy HTTP connection manager (`normalize_path`, `merge_slashes`, `path_with_escaped_slashes_action`) and its edge best practices; Caddy request matchers and `trusted_proxies`; Spring Framework "Forwarded Headers"; GHSA-4987-27fx-x6cf, GHSA-6p68-w45g-48j7, GHSA-gm3x-23wp-hc2c, CVE-2024-45410, CVE-2022-31813, CVE-2026-27587; http 1.5.0 `src/uri/path.rs` (bytes accepted raw in a path).

## D48. DNS checks: our own small provider trait, lego's wait, TSIG verified both ways

Wildcards and names Let's Encrypt cannot reach are checked with DNS-01 (RFC 8555 section 8.4): a TXT record at `_acme-challenge.<name>` whose value is the base64url SHA-256 of the key authorization (instant-acme `dns_value()`). A wildcard's authorization carries the bare name (section 7.1.3), so `*.example.com` and `example.com` share one TXT name and two values; every provider adds its value next to others and removes only its own (Let's Encrypt: "You can have multiple TXT records in place for the same name").

- **Providers.** `letsencrypt.dns` is a list of entries, each with `domains` and one provider; a name takes the entry with its most specific domain through `burrow_syntax::web::dns_entry_for`, shared by validate and the server. No provider crate fits (crates.md 4b: the candidates add 4.5 MB or do not build on ring), so a trait of two calls, `present` and `cleanup`, has four implementations:
  - Cloudflare's API v4 on our HTTPS client: zone found by walking up the name (`GET /zones?name=`, `active` zones only; a `pending` zone is named in the error, since its records are not public), the TXT content sent quoted as the API documents, TTL 60 (the minimum outside Enterprise), error 81058 ("an identical record already exists") taken as success with the record id looked up so cleanup still removes it, records found again by `name.exact`/`content.exact` after a restart, a 429 shown with its `retry-after`. The token header is marked sensitive.
  - RFC 2136 dynamic update over TCP (section 7.8: only TCP gives an accurate response code), signed with TSIG hmac-sha256 by default (RFC 8945 section 6: MUST implement and RECOMMENDED; BIND's `tsig-keygen` and Knot's `keymgr` default), or hmac-sha384 or hmac-sha512 with `algorithm` (owner decision 0v, since the algorithm must match the server's key; hmac-md5 and hmac-sha1 are refused, RFC 8945 section 6), fudge 300 s (section 10). The zone is found by an SOA walk at the configured server, accepting only an authoritative answer, as certbot-dns-rfc2136 and lego do; no zone key is needed. Add is a class-IN add (a duplicate is ignored, section 2.5.1) and delete is class NONE with the exact rdata (section 2.5.4), never lego's delete-the-RRset, which would drop a wildcard's other value. Every answer's TSIG is verified (RFC 8945 section 5.4, hickory-proto's `TSigVerifier`, MAC and time); an unsigned answer is accepted only as a NOTAUTH error, and BADKEY, BADSIG and BADTIME each get their own text.
  - acme-dns: one `POST /update` (`X-Api-User`, `X-Api-Key`, sensitive); it keeps two values per subdomain, so cleanup does nothing. The CNAME target must start with the configured `subdomain`, otherwise the error names the CNAME to add. Its API is often plain HTTP on a LAN, so `http://` is accepted only when every address of the API's host is loopback, RFC 1918 private (10/8, 172.16/12, 192.168/16) or an RFC 4193 unique local address (fc00::/7), checked at validate and again before connecting (owner decision 0v); burrow connects to the address it checked, so a name cannot resolve to a public address in between. Link-local addresses (RFC 3927, fe80::/10) and the shared address space 100.64/10 (RFC 6598, which a carrier shares among its customers) are not private here. Anything else needs `https://`.
  - a command, lego's `exec` convention (`present|cleanup <fqdn with final dot> <value>`), 60 s at most and then killed, an empty environment except `PATH` (and `SYSTEMROOT` on Windows, which Windows programs need to start), its stderr (else stdout) in the error, no secret passed.
- **CNAMEs (owner decision 0t).** `_acme-challenge.<name>` is followed through the resolvers for at most 8 CNAMEs (lego follows 50, Let's Encrypt's Unbound about 10); a loop or a ninth step is an error naming the chain. The record is written at the final target, the provider is still the entry of the name's own domain, and when Cloudflare or RFC 2136 cannot write the target the error names the entry to list the domain on; a wildcard CNAME that catches `_acme-challenge` (a known lego pitfall) adds its own hint. acme-dns and the command take the target as it is.
- **Waiting (P6-05, owner decision 0t).** After every value is set, burrow finds each record's zone by an SOA walk and the zone's NS through `resolvers` (or the system's: `/etc/resolv.conf`, the adapters' DNS servers on Windows, else 1.1.1.1, 8.8.8.8 and 9.9.9.9, named in the summary), then asks every address of every NS directly (RD=0, EDNS 1232, TCP on truncation) every 3 s, for at most `wait_secs` (120 s, Caddy's default). An NS counts when every address it can reach answers authoritatively with all the values; an address with no route from here (an IPv6 NS on an IPv4-only host) is skipped, a silent one is retried until the limit, a REFUSED or non-authoritative answer stops at once with the NS named. TXT is never asked of a resolver. Let's Encrypt checks from several places at once (from 2026-11-10 seven lookups), so one lagging NS is the usual failure. `set_ready` is called only when every value is everywhere: a timeout leaves the authorizations pending, so it never counts as a failed validation (5 per name per hour).
- **Order flow.** An order answers every authorization first (TLS-ALPN and HTTP-01 in memory, DNS values collected), then sets and waits for all DNS values, then calls `set_ready` on each. Checks are per name (C9): in a certificate with a DNS name and other names, the DNS names use DNS and the rest keep TLS or HTTP. Every value set is removed after the order, on success and failure alike; a dropped order removes them on a spawned task, and each value is listed in `<state>/dns-pending.json` (0600) before it is written and taken off after cleanup, so values left by a crash are removed on the next start (given up with a log line after 7 days).
- **Shared wildcards (owner decision 0l).** `wildcards` on an entry make one certificate per wildcard with its parent name, ordered like a service's; sites one label under it, its parent name and a site's own wildcard host use it and order nothing. A name with its own `tls` file or an exact `web.certificates` entry keeps that.
- **Secrets** (`token`, `secret`, `password`) are held in `Secret` (`Arc<Zeroizing<String>>`, `Debug` prints `<secret>`). Accepted (industry standard): header values and hickory's `TSigner` key are plain copies for one request and are not zeroized.
- **Not in v0.2.0: dns-persist-01.** Let's Encrypt said on 2026-06-25 that it will not deploy it until the IETF draft's open issue about client-computed record information (draft issue #64) is resolved, and had not shipped it as of 2026-10-25.

## D49. Access control: allow_from first, one wrong-password limit, forward auth that fails closed, device certificates per name

A site's checks run in a fixed order before its app is opened: the service's `allow_from`/`deny_from` (403), `maintenance`, `rate_limit` (429), `basic_auth` (401, 429, 503), then `forward_auth`. The address check comes first so a denied address learns nothing about passwords and costs no hashing; `visit()` still checks it again when the stream opens.

- **Passwords.** `burrow passwd` writes argon2id with OWASP's parameters (m=19456 KiB, t=2, p=1; `argon2::Params::DEFAULT`); bcrypt `$2a$`, `$2b$` and `$2y$` are accepted for pasted hashes (`caddy hash-password` writes `$2a$`), while `$2x$` (the old buggy variant), argon2i and argon2d are refused. The cost comes from the hash, so a pasted one is capped (argon2 m ≤ 65536 KiB, t ≤ 10, p ≤ 4; bcrypt cost 4 to 14) by `burrow_web::auth::check_hash`, which validate and the server share. At most 2 checks run at once on blocking threads, a request waits at most 1 s for a slot and then gets 503, and an unknown user is checked against a dummy argon2id hash so it costs the same. Successes are cached for 10 minutes under an HMAC-SHA-256 (aws-lc-rs) of the length-prefixed user, password and stored hash with a per-process random key, at most 1024 entries; a changed hash misses. The argon2 and bcrypt crates compare in constant time (password-hash `Output`, `subtle`). The `Authorization` header never reaches the app; the challenge is `Basic realm="<service>", charset="UTF-8"` (RFC 7617). **From the admin UI (owner requirement):** a write admin's new password travels once over the admin channel in a `hash_password` request; the server hashes it with the same function as `burrow passwd` (`burrow_web::auth::hash_password`), keeps only the hash as a one-use handle (like a generated secret, at most 16 per session for 30 minutes), and a `password_set` operation writes `user: <hash>`. The password itself is held in `Zeroizing` once parsed and is never stored, logged, audited or sent back; stored hashes reach the UI only as "set", and a `$hash` marker cannot be written back. A pasted hash is checked once, by validate on the server (`burrow_web::auth::check_hash`), and shows in review like any other problem. Accepted risk: the request's JSON buffer is freed but not wiped, as in any web form.
- **Wrong passwords (owner decision 0v).** Even without `rate_limit`, 10 wrong passwords per minute per visitor (IPv6 per /64, `::ffff:a.b.c.d` as IPv4) are allowed, then 429 with `Retry-After` until the budget refills, for the right password too. Missing or unreadable headers are not counted.
- **Rate limits.** governor with `std` only (no dashmap, quanta or jitter), a keyed GCRA bucket per site: `rate_limit` per second with a burst of twice that, as Traefik's average/burst. Keys are the visitor after `trusted_proxies`, IPv6 by /64 (owner decision 0r; Traefik `ipv6Subnet`), through the same `subnet_key` as the pre-TLS permits. Every keyed limiter, the wrong-password list and the cache are swept every 60 s (`retain_recent`, `shrink_to_fit`), so a burst of new addresses cannot grow memory over the years. A reload keeps a site's bucket when its rate did not change.
- **Forward auth.** The visitor's copies of `copy_headers`, also with `_` read as `-` (`Remote_User`), are removed before the check whatever the login service answers (Caddy CVE-2026-30851 and CVE-2026-52845), after the names listed in `Connection` are removed, so `Connection: Remote-User` cannot remove what burrow adds (Traefik CVE-2024-45410 class). The check is a bodiless GET to the login service through the same seam, with the visitor's address (the login service's own `allow_from` and connection limits apply): no `Content-Length`, `Transfer-Encoding`, `Expect`, `Upgrade` or hop-by-hop headers, the visitor's `Forwarded`, `X-Forwarded-*`, `X-Original-*` and their underscore forms removed, and `X-Forwarded-Method/Proto/Host/Uri/For` plus `X-Original-URL`, `X-Original-URI` and `X-Original-Method` set by burrow from the cleaned public path, so both of Authelia's endpoints (`/api/authz/forward-auth`, `/api/authz/auth-request`) and authentik's nginx endpoint see what routing saw (authentik GHSA-5wcc-hf24-rf5h trusted a visitor's `X-Original-URI`). `Host` stays the visitor's (Caddy). A 2xx copies every value of each `copy_headers` field and nothing else (no `Set-Cookie`); its body is dropped with its connection, which is never reused. Any other answer goes back to the visitor with its hop-by-hop headers removed (the login redirect, 401, 407). No answer within `response_header_timeout_secs` is 504, a login service that is down 502 or 503: it never fails open. The subrequest opens the login service without the "this host leads to the service" check that visitor connections get, since its Host is the protected site's; only this code path can open such a stream. `basic_auth` and `forward_auth` on one site is a validate error (owner decision 0v). No Rust crate does forward auth on hyper 1, so it is about 150 lines on the existing seam.
- **Named login services (decision 0za, 2026-10-30).** `web.forward_auth` is a map of login services by name, and a site picks one with `forward_auth: <name>`; `true` is shorthand only when exactly one is defined, and the admin UI always writes the name. Each login service is written once, as Traefik's named middlewares and Pomerium's per-route settings are, so there is no shared default versus a site's own copy. Every site with `forward_auth` removes the visitor's copies of the `copy_headers` of all login services, and copies from a yes only its own, so a site on Authelia does not let a visitor's `X-authentik-username` through to an app that still trusts it. The site of any login service's `service` never has `forward_auth`. The admin entity `login` lives at `web.forward_auth`, so renaming one renames it on every site that names it.
- **Device certificates.** A rustls verifier belongs to a whole `ServerConfig`, so a name with `client_auth` gets its own config, chosen after the ClientHello peek (D44), built with `WebPkiClientVerifier::builder_with_provider` (aws-lc-rs) and the shared certificate resolver; each has its own session cache and no ticket key (rustls' default ticketer makes no stateless tickets), so a session made on an open name never resumes on a protected one (rustls also refuses resumption across SNI, RFC 6066 section 3). A name under a wildcard takes the wildcard's setting only when it has no exact site of its own, and Host must equal SNI (421), which closes the bypass of Traefik CVE-2026-48491 over one wildcard certificate. A visitor without SNI (an IP-address site) gets a fresh config with the same verifier.
- **Revocation (owner decisions 0r and 0v).** `client_auth.crl` holds one or more CRLs (PEM or DER, like nginx `ssl_crl`), each signed by any CA in `client_auth.ca`, so a two-tier CA like step-ca works with only its intermediate's CRL. The verifier is `with_crls` plus `allow_unknown_revocation_status`: a device is refused only when a CRL lists it, and a tier without a CRL never refuses everyone. A CRL past its nextUpdate still applies (rustls' default; nginx and OpenSSL refuse the handshake instead, which locks every device out on a late publish), and status and validate say so. rustls-webpki keeps its CRL signature check private, so burrow reads the CRL with x509-cert and verifies its signature with the same rustls/aws-lc-rs algorithm list webpki uses, matching the CRL's and the CA's algorithm identifiers; validate and every reload run it. Version 1 CRLs without extensions are refused with the `crlnumber` fix for OpenSSL. The files are watched with the certificate files; on a change, new files build a fresh config (a new session cache, so a revoked device cannot resume a TLS 1.3 session whose chain rustls would restore unchecked), unchanged bytes keep the old one, and files that fail to read, parse or verify keep the last good config with a warning in status and the log; a site whose files were never good refuses every visitor. `client_auth` is refused on a name that carries the tunnel (owner decision 0v).

Accepted risks (industry standard): a revoked device's connections that are already open stay open until they close, as in nginx; bcrypt reads at most 72 bytes of a password, as htpasswd and Go do.

## D50. burrow mcp: the admin channel for AI apps, read-only by default, applying only checked plans

`burrow mcp` is an MCP server (rmcp 3.7.0, the official Rust SDK, with only `server`, `macros`, `schemars`, `transport-io` and `transport-streamable-http-server`) that runs on the admin's machine with a visitor config and speaks the same admin protocol as the burrow admin UI, through the shared `admin_link` unit (config lookup, the Noise admin channel, the private state folder, the token). The server is unchanged and gets no new port or field: the visitor's `admin: read | write` is the permission, and every server rule (D39, the references rule, locks, history) applies as for the UI.

- **Tools.** Seven fixed tools, each one admin request: `get_status` (status event), `get_config` (state), `describe_settings` (schema, optionally one path), `list_versions` (history), `check_change` (validate), `revert_to_version` (revert) and `apply_change` (apply). No per-key tools: the settings come live from the server's schema, so new keys need no MCP change. `generate_secret`, `connect_info`, uploads and password hashing are not offered, since they return or take secrets. `check_change` is listed only when the server grants `write` (the server's validate needs it); `apply_change` and `revert_to_version` only with `--allow-write` too.
- **Only checked changes are applied.** `check_change` and `revert_to_version` keep the plan id with its base and operations in memory (at most 16 plans, 30 minutes, like the admin session's pending caps); `apply_change` takes only a plan id and the confirmations, and sends the protocol's existing `apply {base, ops, plan, confirm}`. So the AI cannot apply anything it did not check, the server refuses a config that changed since (conflict), and impacts that need confirming must be named. A revert is the same two steps, as in the UI.
- **Secrets.** Results carry what the UI gets: secrets as fingerprints or `${ENV}` names. An apply result has secret values and connect snippets removed. The e2e tests scan every tool result for every secret of the test server.
- **Prompt injection.** Names, hosts and other text in results can come from outsiders; the tool descriptions and the server instructions say that results are data, not instructions, and such values stay in JSON fields. Nothing applies without a plan the user can see.
- **stdio** is the default (no port, no token); logs and notes go to stderr only (MCP 2026-07-28 stdio binding).
- **Streamable HTTP (`--http`)** runs on our own hyper server with rmcp's Tower service (no axum), on 127.0.0.1:7838 only (7838 because 7840 is init's example service port). rmcp's own checks are used rather than our own: Host must be `127.0.0.1:<port>` or `localhost:<port>`, an Origin other than `http://127.0.0.1:<port>` or `http://localhost:<port>` gets 403 (the spec's MUST), and the body is capped at 1 MiB (413). burrow adds the bearer token (401, constant-time compare, the file read on a blocking thread), a 5 s header timeout, a 10 s body timeout, one request per connection (each MCP request uses its own connection, which costs nothing on a loopback listener), a refusal that closes without reading the body, and at most 8 connections, so a slow local client cannot hold the slots. It is stateless: GET and DELETE get 405 and `Mcp-Session-Id` is ignored, for 2025-11-25 clients too (`with_legacy_session_mode(false)`). A missing `MCP-Protocol-Version` is taken as 2025-03-26, which the spec allows ("A server that supports clients implementing protocol versions earlier than 2025-06-18 ... MAY treat a request that omits the header as protocol version 2025-03-26"); requiring it would also refuse 2025-11-25 clients, whose `initialize` may omit it. A mismatched or unsupported version gets 400 (HeaderMismatch -32020 from rmcp).
- **The token (owner).** 256 random bits, made once per visitor config and kept 0600 as `mcp-<digest>.token` in the private admin state folder (D40's folder; the session sweep never touches it), so the app's setup survives restarts. It is read from the file on every request and compared in constant time against that value only, so `--new-token` stops the old one at once, also in a running server, and a missing, unreadable or malformed file lets nobody in. A file that others can read, or that is not a token, is refused and never overwritten. It is never a command-line argument. The start prints the URL, the header and the `--print-config` hints by default, like Jupyter's token link; `--no-print-token` prints only the URL for logs and services. `--print-config claude | codex | cursor` prints a ready setup for that app, formats checked against each app's docs; the first line names the file or the command as a comment (on stderr for Cursor, since JSON has no comments, so its output stays a valid file), and Codex gets `bearer_token_env_var` with the export line on stderr, so its token stays out of config.toml.

- **Everywhere (owner).** `burrow mcp` is in every release build on Linux, macOS and Windows, with no cargo feature and no OS gate. The token file is written with burrow's private writer (0600, or an access list for the user alone on Windows), and the note for a person who starts it in a terminal uses `std::io::IsTerminal`, which works on Windows too.

## D51. HTTP/2 hardening is proved by configuration tests, the watchdog, h2spec, upstream regression tests and a memory measurement, not by attack traffic

The owner chose (2026-10-26) to prove decision 0s without sending crafted attack frames from our tests. Five things prove it together:

- **Every limit is pinned.** `http/h2.rs` holds the limits in one place, and the visitor server, the h2c/TLS app client and the HTTP/1.1 app link are built from it. A unit test checks each value and reads hyper's own builders, so a changed limit fails the test: 100 concurrent streams; 20 pending-accept resets (Rapid Reset); 256 local error resets (RUSTSEC-2024-0003, MadeYouReset); stream window 256 KiB and connection window 1 MiB, with no adaptive window; 16 KiB frames; a 32 KiB decoded header list; a 4,096-byte HPACK table; a 32 KiB send buffer per stream; a PING every 30 s answered within 20 s; and 100 header fields per request (431). An integration test reads the SETTINGS frame and the connection WINDOW_UPDATE the server really sends.

- **h2spec** 2.6.0 passes all 146 non-strict cases in CI's h2 job.
- **Upstream regression tests.** The pinned h2 0.4.20 and hyper 1.12.0 (Cargo.lock; `cargo deny check advisories` is clean) carry the fixes, and h2's own tests prove them (tagged sources, github.com/hyperium/h2/tree/v0.4.20):

  - CONTINUATION (VU#421644): `server.rs` tests `too_many_continuation_frames_sends_goaway`, `abusive_headers_send_goaway` and `too_big_headers_sends_reset_after_431_if_not_eos`.
  - MadeYouReset (VU#767506): `flow_control.rs` test `too_many_window_update_resets_causes_go_away`.
  - Empty and small DATA frames (RUSTSEC-2026-0258): `stream_states.rs` tests `too_many_empty_data_frames_sends_goaway` and `too_many_small_data_frames_sends_goaway`.
  - The HPACK decoder: `src/hpack/decoder.rs` test `test_decode_indexed_larger_than_table`, `src/frame/headers.rs` test `test_try_append_prevents_panic_on_max_size_reached`, and `server.rs` test `server_builder_header_table_size`.
  - hyper passes our limits to h2 in `src/proto/h2/server.rs` (github.com/hyperium/hyper/tree/v1.12.0).
- **Memory under heavy legitimate load.** The test server runs as its own process (the test binary started again as a child), and its VmHWM is read from /proc. N connections each keep 100 streams busy: 48 downloads of 1 MiB, 47 uploads of 1 MiB, and 5 slow readers taking 512 KiB at 64 KiB/s. Per connection = (VmHWM − idle RSS) / N:

  | App | N = 10 | N = 50 |
  |---|---|---|
  | h2c (`target_http2`) | 6.4–7.1 MiB | 5.3–5.4 MiB |
  | HTTP/1.1, 32 KiB app read buffer | 9.9–10.5 MiB | 8.2–8.3 MiB |

  The aim is about 8 MiB. The gated test (`tests/h2/load.rs`, `BURROW_H2_SLOW`) allows 16 MiB, so only a real regression fails it. N = 10 is the default and runs in CI; N = 50 is run by hand with `BURROW_H2_LOAD_CONNS=50` (2 runs, release build, a 10-core Linux VM). Both columns were measured on 2026-10-31 on the same VM. Each figure divides all of the server's memory growth by N, so it also carries a fixed part: the two columns together give about 24 MiB (HTTP/1.1 app) or 16 MiB (h2c) once, plus about 7.8 or 5.1 MiB per connection. That is why N = 10 reads higher, and the cost of one more connection meets the 8 MiB aim. N = 10 first read 8.1–8.2 and 5.1–5.5 MiB on 2026-10-30; the commit that recorded those gives 9.6–10.0 and 6.2–6.4 MiB on this VM today, so the difference is the host, not a regression.
- **At N = 50 an answer may take longer than 10 s, so the deadline grows with N.** Each answer must still come within 10 s × N / 10 (50 s at N = 50), with status 200 and the full body. The measured process runs on 2 worker threads, and both of them are busy all the time from N = 10, so it moves a fixed number of bytes per second; with 5 times the bytes in flight, each answer takes about 5 times as long (Little's law). Measured over 3 runs at N = 50 with an HTTP/1.1 app: every request (12,000 to 16,000 a run) got 200 and its full body, and the watchdog cut none, but an upload's answer took up to 12.2 s (median 4.0–4.7 s) and a download took up to 12.6 s to finish. Part of that is the test host: 5,000 app connections have both ends on the same machine, and the test app writes download bodies faster than visitors take them, so about 850 MiB waits in kernel socket buffers (the app's send queues and burrow's receive queues). That reaches the kernel's TCP memory limit (`net.ipv4.tcp_mem`), and the kernel drops packets and resends them after timeouts. That memory is the kernel's, not burrow's, and VmHWM does not count it. The h2c app uses 50 app connections with HTTP/2 flow control and never reaches that limit; its slowest answer came in 5.4 s. The load is still the same: every stream is busy the whole time, so each connection holds its 100 streams at once, and the per-connection numbers are lower than at N = 10, because the fixed part is shared by more connections.
- **One app connection per HTTP/2 stream.** Measuring found a deadlock: an HTTP/2 visitor connection could use only 8 app connections. Each waiting upload had already been sent a full 256 KiB stream window, so 12 parallel 1 MiB uploads to an HTTP/1.1 app filled the 1 MiB connection window. The 8 running uploads then never got their last bytes, and all of them got 504 after 60 s. Now an HTTP/2 visitor connection may open up to `max_concurrent_streams` (100) app connections, like nginx and Caddy, which open one upstream connection per stream. The p5-research memory model already assumed this; HTTP/1.1 visitors keep 8. The service's `max_connections` still caps the total, and the extra streams get 503 at once. Tests: 16 parallel 1 MiB uploads all finish; with `max_connections: 4`, 16 uploads get only 200 or 503, within seconds.
- **The app read buffer is 32 KiB** (it was 40 KiB). That is the low end of p5-research's 32–40 KiB, and it still holds the largest response head (32 KiB, MAX_HEAD). With one app connection per stream, it brings an HTTP/1.1 app from 8.6–8.8 MiB per connection (40 KiB, N = 10) to 8.1–8.2 MiB. That is a little over the 8 MiB aim, so the test's bound stays at 16 MiB.
- **An app with a small listen backlog can reset uploads under a burst, and burrow answers 502.** One app connection per stream means an HTTP/2 visitor can open up to MAX_STREAMS app connections at once. An app whose listen backlog is smaller than that burst overflows its accept queue; the kernel falls back to SYN cookies, and a later packet of a multi-packet request (an upload) can fail the cookie check and be reset. burrow answers that reset with 502 and does not retry the request, as nginx does for a request whose body was sent. This is accepted: the app sets its own backlog (burrow's own listeners use 4096). The h2 load test's app uses 4096 too, after this burst reset its uploads on a busy CI runner.

## D52. The 32-bit ARM builds read the clock with 32-bit time until Rust moves to 64-bit time

On 19 January 2038 a signed 32-bit count of seconds since 1970 runs out. Most release builds are not affected: Linux amd64, arm64 and riscv64, macOS, Windows and FreeBSD use a 64-bit time, certificate dates already cover years after 2050, and timeouts use the time since boot. The `linux-armv7` and `linux-armv6` builds (musl, 32-bit) are. On 32-bit musl the `libc` crate still defines a 32-bit `time_t` unless an unstable cfg turns on 64-bit time (libc 0.2.190, `build.rs`), and the standard library's `SystemTime::now` calls that `clock_gettime` (Rust 1.99, `library/std/src/sys/pal/unix/time.rs`; only 32-bit glibc tries `__clock_gettime64` first). musl 1.2 keeps that old call for compatibility and turns a time that does not fit into an error, and the standard library treats an error there as impossible and panics. Check again whenever `rust-toolchain.toml` moves to a newer Rust: if `SystemTime::now` on `armv7-unknown-linux-musleabihf` uses a 64-bit clock call, this decision can go.

## D53. jemalloc runs its background purge threads, so an idle server gives memory back

An idle server kept the memory of its last busy minute. In the soak calibration (musl + jemalloc release build), the server's RSS stayed at 2.27 GB through a 60 s idle rest after an overload step, then fell to 864 MB within 10 s of the next load. A local repeat (one minute of 800 HTTP/2 requests per second through the web proxy, bodies 64 KiB to 8 MiB, then 4 minutes idle) gives the same picture: the RSS went from 15 to 563 MiB and was still 539 MiB after 4 minutes of idle.

The memory was free, but jemalloc had not returned it. jemalloc keeps freed pages as "dirty" and returns them over `dirty_decay_ms` (10 s by default), but without background threads it does this work only when the program allocates or frees again; its own tuning guide says background threads avoid "unintended purging delay caused by application inactivity". A shorter decay does not help an idle program: with `dirty_decay_ms:1000` the same run still held 543 MiB after 2 minutes. With `background_thread:true` it fell from 577 to 91 MiB within 10 s and to 29 MiB within 30 s; the release build with this change did the same (574, 84, 27 MiB), and with the option turned off again it kept 553 MiB.

So the jemalloc builds (Linux amd64, arm64 and riscv64) turn on tikv-jemallocator's `background_threads` feature, which builds jemalloc with `background_thread:true` and keeps the 10 s decay. The cost, measured on the same runs: 4 more threads (jemalloc's `max_background_threads` default is 4) that sleep between purges, 0.13 s of CPU in 4 idle minutes against 0.1 s without them, the same peak RSS and latency under load (p99 17.9 against 17.7 ms), and no change in binary size (16,550,312 against 16,550,376 bytes, musl amd64). The option can still be turned off at run time with `_RJEM_MALLOC_CONF=background_thread:false` (the `_RJEM_` prefix comes from tikv-jemallocator's prefixed symbols). Redis ships the same default (`jemalloc-bg-thread yes`). tikv-jemalloc-sys 0.6.1 still warns that background threads are unsupported on musl; that entry dated from a missing `pthread_create` symbol in static builds, which jemalloc 5.2.0 fixed, and tikv/jemallocator pull 191 removed it. The musl amd64 build above started its background threads and purged, and so did a small test program built the same way for musl arm64 (64 KiB pages) and riscv64 and run under QEMU user mode.

The 32-bit ARM builds use mimalloc (D12), which has no background thread either: it purges freed memory after `purge_delay` (1 s in mimalloc 3), but only from inside a later allocation or free. Those builds may keep their peak while idle in the same way; this was read from the sources, not measured.

## D54. One visitor address gets a fair part of a busy service or client, with no new limits

A security test (2026-10-31) found that one address could deny a client's websites to everyone else. It opened about 82 HTTP/2 connections, each with 100 POST requests whose body never came. Every stream holds its own app connection (D51), so the 8192 forwarded connections of the client (`limits.max_connections_per_client`) filled up, and every other visitor of that client's sites got `503` until the requests timed out after 60 s (`response_header_timeout_secs`) and were sent again. A service with its own `max_connections` fills sooner.

What others do by default, checked 2026-10-31:

- **nginx** reads the whole request body before it contacts the app (`proxy_request_buffering on`). Up to `client_body_buffer_size` (8 or 16 KiB) is kept in memory and the rest goes to a temporary file. A body may be at most 1 MiB (`client_max_body_size`), and a body that stops for 60 s gets `408` (`client_body_timeout`). Answers are buffered too (`proxy_buffering on`). `worker_connections 512` with `worker_processes 1` caps all connections, but nothing caps them per address unless `limit_conn` is configured. So a stalled body never reaches the app.
- **Caddy** streams request bodies to the app (`request_buffers` is opt-in), has no limit on app connections (`max_conns_per_host`: "No limit") and no body timeout (`read_body`: none). A stalled request holds an app connection, but there is no cap, so it costs memory and file handles instead of a `503`.
- **Traefik** streams too; its `buffering` middleware is opt-in. Its entry points end a request that is not read within 60 s (`readTimeout`, which covers the body, as Go's `Server.ReadTimeout` does), and it has no cap on app connections.

So the `503` comes from burrow having a cap at all; Caddy and Traefik have none, and nginx avoids it by buffering. The owner chose (2026-10-31) to add **no new limits and no settings**: no global connection cap and no default `max_connections` for websites. Instead, the existing caps are shared fairly, with the rule burrow already uses for connections that have not finished their handshake (`limits.max_handshakes`, docs/protocol.md):

- **The rule.** Once fewer than half of a pool are free, one visitor address may hold at most an eighth of the pool, and at least 8. It applies to two pools: a service's `max_connections` when it is set, and its client's forwarded connections (`clients.<name>.max_connections` or `limits.max_connections_per_client`). An address over its part gets `503` at once, the same answer as a full pool (D51), and it does not wait. Waiting would keep the request and its buffers in memory, which is what the rule is meant to free. A visitor below half of a pool is never refused by this rule.
- **The address.** It is the visitor's address as `allow_from` sees it: the TCP peer, the address in a PROXY header from `web.proxy_protocol_from`, or the real client from `X-Forwarded-For` when the peer is in `web.trusted_proxies`. IPv6 addresses count per /64. Loopback addresses have no part, as in the handshake rule: they are a local proxy or the machine itself, and a local proxy without `trusted_proxies` would otherwise share one part among all its visitors.
- **Where it applies.** The rule covers connections from the web proxy only: sites, passthrough sites and login services. A service's `bind` port and `burrow visit` keep today's behaviour, because their pools were not part of the finding and a raw TCP connection carries little memory.
- **One implementation.** The rule lives in `burrow-syntax` (`share`) and is used by the web proxy's pre-TLS handshake count, the tunnel's handshake count and the new forwarded-connection count, replacing two copies.

Measured on 2026-10-31 with the finding's repro (90 HTTP/2 connections of 100 stalled POSTs each, so 9,000 streams), the musl release build and the security lab's config (client `self`, 8,192 connections), while a second visitor asked 10 times during the attack:

- From one non-loopback address: 4,097 streams were held, which is half the pool and one more, and the other 4,903 got `503` at once. The second visitor got `200` all 10 times; before this change it got `503`. The server's RSS went from 16 to 223 MB, with 4,206 open files.
- From a trusted proxy (`127.0.0.2`) carrying `X-Forwarded-For: 203.0.113.7`: the same numbers, with the access log naming 203.0.113.7.
- With `max_connections: 1024` on the service and 20 attacking connections: 513 streams were held, 1,487 got `503`, and the second visitor got `200` all 10 times.

`tests/web/shares.rs` checks the same thing with a pool of 16, both for a service and for a client: one address keeps 9 and gets `503` for the rest; another address, an IPv6 address and a loopback visitor get `200`. On the commit before this change, the address kept all 16. A further test checks that two real clients behind one proxy each keep 7 with nothing refused.

Known limits. An attacker with many addresses still gets an eighth of a pool per address, so 8 IPv4 addresses (or 8 IPv6 /64s) can fill it, as with the handshake rule. A request whose body comes in full but whose answer is read slowly still holds its app connection, because burrow streams answers. Both are what Caddy and Traefik accept by default. Full nginx-style buffering (request bodies before the app is contacted, with a size threshold, a temporary file and a body timeout, and answers too) would close both. It is a candidate for v0.2.1, after the benchmark run (BENCH-1) shows its cost in memory, disk and latency. It needs exceptions for streaming bodies such as gRPC, and a per-connection budget, because 100 streams of 64 KiB is 6.4 MiB against about 1 MiB of window today.

## D55. TLS prefers the post-quantum hybrid X25519MLKEM768, with rustls' aws-lc-rs provider

All of burrow's TLS prefers the hybrid key exchange X25519MLKEM768 (ML-KEM-768 with X25519) and falls back to X25519, P-256 and P-384 (owner, 2026-10-31: burrow does not leave out what others have by default). - **The provider.** rustls 0.23.46 with its default provider, aws-lc-rs, and its `prefer-post-quantum` feature, which puts X25519MLKEM768 first. ring has no ML-KEM, and rustls does not plan ML-KEM outside aws-lc (rustls issue 2763). - **Builds.** aws-lc-sys needs only a C compiler: zig through cargo-zigbuild on the Linux, Windows and FreeBSD targets, Xcode's clang on macOS. Windows x86_64 takes rustls' `prebuilt-nasm` objects, so no NASM is installed. The armv6, armv7, aarch64 and riscv64 release binaries under qemu-user and the x86_64 Windows binary under Wine each agreed X25519MLKEM768 with a Go 1.26 client on the web proxy and on `wss://`, and X25519, P-256 and P-384 with clients that offered only those; the macOS targets build in CI.
- **Risk accepted.** A large C library in every TLS path (memory safety), maintained by AWS, the rustls default and FIPS 140-3 validated with ML-KEM. The fallback, ring with a verified pure-Rust ML-KEM (libcrux-ml-kem) and our own hybrid glue, was not needed, because every target builds.

## D56. The web proxy keeps small, reused buffers per connection, and HTTP/2 answers do not pin the app's read buffers

BENCH-1 found burrow at 1,954 MiB at its peak on the mix (bodies up to 8 MiB), against 209 MiB for nginx. Per connection burrow was already lean on small requests; the gap was buffers that grew and stayed, buffers allocated and zeroed again for every tunnel record, and one HTTP/2 effect that grew without a bound while connections stayed open. Five changes, each measured on its own, with no new setting and no wire change:

- **HTTP/1.1 visitors.** hyper's visitor connection had no `max_buf_size`, so its read buffer could grow to hyper's default of 400 KiB. The connection wrappers did not pass on vectored writes, so hyper copied every body chunk into one write buffer that grew to about 512 KiB and kept that size for the connection's life. The visitor connection now keeps at most 64 KiB each way (`VISITOR_BUF`, above the 32 KiB header limit), and `Watched`, `Prefixed` and `Pipe` pass on `poll_write_vectored`, so hyper queues the chunks it gets instead of copying them.
- **Tunnel records.** Every record received took a fresh 128 KiB zeroed buffer, even a tiny one, and every pump took and zeroed 64–128 KiB more whenever its source paused for a moment. The buffers now come from a small pool shared by the process (at most 64 buffers of 64 KiB, 4 MiB), and the read buffer holds one record instead of two. An idle reader still holds no big buffer: it reads up to 530 bytes into its own small array, so a small record costs one read call instead of two. Data just over 512 bytes goes as one record instead of two. Records keep their sizes and their format, so v0.1.x peers are unaffected.
- **The in-memory pipe** between the web proxy and the tunnel holds 32 KiB each way instead of 64 KiB.
- **HTTP/2 answers carry their own header values.** hyper's HTTP/1.1 client keeps an app's response header values as slices of its read buffer. The HPACK encoder of a visitor's HTTP/2 connection keeps up to 4 KiB of recent header values for the connection's life, and each entry kept a whole 8–64 KiB app read buffer alive with it. On the repro this grew by about 1 KB per request with no bound, up to about 1.4 MiB per connection. An answer to an HTTP/2 visitor now copies its header values into their own small allocations first.
- **Not done: `self` straight to the app.** D38 sends `self` through the same target code as a remote client, and that stays. The direct path would only be worth it if a clear gap remained, and then only after the target rules are shared by both paths; the numbers below show the gap is small.

Measured on 2026-10-31 on a 10-core VM, with the musl and jemalloc release build. 300 open connections (k6, closed set) to a `client: self` site and to a site behind a remote client over TCP, 4,000 requests a second, 30 s measured. The figures are the mean of two rounds, which agree within a few percent. PSS is the server's average while measured, CPU is µs·core per request.

## D57. A web connection without a handshake slot waits for one instead of being dropped, and `limits.max_handshakes` is 2048

BENCH-1 found that burrow's limits on tiny requests and on new connections were set by errors, not by CPU or latency: k6 saw `EOF` on new TLS connections at the moment it added users, all from one address. The web port dropped a connection at once when the pre-TLS pool (`limits.max_handshakes`, 256) was full, and one address was cut off at about 129 once more than half of the pool was in use.

What others do by default, checked 2026-10-31: nginx has no limit on TLS handshakes, only `worker_connections`, and bounds a handshake with `client_header_timeout` (60 s). Go's `net/http`, and so Caddy and Traefik, have no cap on connections or handshakes and give a handshake `min(ReadHeaderTimeout, ReadTimeout, WriteTimeout)` (Go commit b59467e0, issue 48120). HAProxy stops accepting when `maxconn` is reached, so new connections "go into the kernel's socket queue". Envoy's edge guide sets a listener `connection_limit` of 10,000 and closes connections above it. Nobody caps handshakes per address; slow clients are handled with timeouts.

The web listener now works like HAProxy, with no new setting:

- **Wait, do not drop.** A connection that finds every slot taken waits for one, reading nothing, until its own `limits.handshake_timeout_secs` deadline. tokio's semaphore is first-in, first-out. The deadline counts from the moment of accept, so a connection lives no longer before TLS than it did.
- **A bounded waiting room, then the kernel.** Up to four times the pool may wait. When the room is full, burrow stops calling `accept()` until a place frees up, and further connections queue in the listen backlog (4096) and then in the client's SYN retries. Nothing is answered with `EOF`.
- **Fair shares, as in D54.** While more than half the waiting room is in use, one address (an IPv6 /64) may wait with at most an eighth of it (at least 8); over that it is closed. A connection counts against its address's share of the slots only once it stalls: no hello 1 second after it arrived, or TLS not finished 1 second after its hello. Under pressure an address over its share loses its stalled connections. A fast burst from one address (a NAT, a company proxy, k6) never stalls, so it is never cut; 400 silent sockets from one address are cut after a second, and a waiting visitor from another address is served about a second later.
- **One deadline for the hello.** The hello was read for up to 10 s, longer than the 5 s handshake deadline it sat in. It now ends at the handshake deadline, so a silent socket holds a slot for at most 5 s.
- **Refusals** (`burrow_handshakes_refused_total`) count an address over its waiting share, a wait that reached the deadline, a stalled connection over its share, and a connection that waited and then never sent its hello.
- **The tunnel listener keeps dropping.** Its peers are burrow clients that retry with backoff, and its tests assert that over-cap connections close at once. Tunnel names on the web port still move to the tunnel's own pool before TLS.

**The default.** Concurrent handshakes are the new-connection rate times the handshake time. At 10,000 new connections a second and 100 ms of internet round trips, that is about 1,000, far above 256. The worst case was measured on 2026-10-31 with the release build: every slot holding a hello of nearly 16 KiB that never completes, plus a full waiting room of silent sockets. The hello reader now keeps only its own copy until a TLS record is complete, instead of a second one inside rustls, which halved the cost of a slot from 52 KiB to 26 KiB. At 2048 slots and 8192 waiting the server grew by 82 MiB (26.2 KiB per slot, 3.75 KiB per waiting connection), under the 100 MiB the plan allowed; 4096 would have been 164 MiB. So `limits.max_handshakes` is 2048, with 10,240 sockets before TLS at most, which installed services allow (`LimitNOFILE=1048576`). The tunnel listener uses the same key.

Measured locally (10-core VM, k6 on the same machine, one address, TLS 1.3, HTTP/1.1, a `client: self` site): with a new connection per request at 12,000 a second, the build before this change gave 6,782 errors (7,706 `EOF` lines from k6), and the build with it gave none; both were CPU-bound (p99 about 1 s, about 300 µs of CPU per connection). At 8,000 a second and below, and on kept-alive tiny requests up to 35,000 a second, both had no errors and the same CPU per request within noise.

**TLS session tickets.** The shared site configurations now issue stateless TLS session tickets (rustls' aws-lc-rs `Ticketer`: keys rotate every 6 hours, a ticket lives 12 hours), as nginx (`ssl_session_tickets on`) and Go and Caddy (tickets on, keys rotated daily) do by default. Before, rustls' stateful cache held 256 sessions, so with many visitors a returning browser often got a full handshake again. Sites with `client_auth` and connections without a name keep rustls' defaults, so a resumed session never skips a client-certificate check. rustls refuses to resume a session for another name (RFC 6066), which a test checks. Accepted risk, as for nginx and Go: a ticket key that leaked would let an attacker decrypt sessions resumed with it until the key rotates.

Sources, checked 2026-10-31: nginx.org ngx_http_core_module (`listen` backlog, `client_header_timeout`) and ngx_http_ssl_module (`ssl_session_tickets`, `ssl_session_cache`); go.googlesource.com commit b59467e0 (Go issue 48120); pkg.go.dev crypto/tls (session tickets); caddyserver.com global options (`timeouts`); haproxy.com "Overload protection" tutorial (`maxconn`, kernel socket queue); envoyproxy.io best practices for edge proxies (`connection_limit`); docs.rs tokio `Semaphore` (fairness); rustls 0.23.46 source (`crypto/aws_lc_rs/ticketer.rs`, `server/hs.rs` `can_resume`, `ServerConfig` defaults); Linux listen(2) and `net.core.somaxconn`.

## D58. After two refused renewal orders with `replaces`, the third try orders without it

The early soak of 2026-10-31 renewed one certificate against Pebble 2.10.1 every 15 minutes for hours without success: every order with `replaces` got a 500 `serverInternal`, "could not find an order for the given certificate: could not find order resulting in the given certificate serial number". Pebble stores a serial without the leading zero byte that DER adds when the top bit is set, but looks `replaces` up with it, so about one certificate in 256 can never be replaced there (Pebble issue #550, fixed by PR #556 on 2026-09-28, not in a release yet). burrow's certificate id is correct: RFC 9773 section 4.1 keeps that byte, and the id is tested against the RFC's example. Until now burrow dropped `replaces` only after `alreadyReplaced`, so any other refusal of the hint repeated until the certificate expired.

- **The rule (owner's coordinator, 2026-10-31, following certmagic).** burrow counts the refusals of orders that carried `replaces`: the CA answered the new order with a problem document that is not `rateLimited`. After two in a row, the third try orders without `replaces`. One transient 500 does not cost the ARI renewal and its rate-limit treatment. Every try still waits for the normal backoff (1 min, 10 min, then 100 min) and runs only once the renewal time has come, so the CA's window is still followed. The count resets when a certificate is issued or a stored one is taken up, so the next renewal sends `replaces` again. Unlike certmagic, the rule applies to every renewal burrow runs, in the background too.
- **Unchanged.** `alreadyReplaced` (and a CA that does not support the field) still drops `replaces` at once. `rateLimited` keeps it and waits for `Retry-After`: at Let's Encrypt an ARI renewal is exempt from rate limits, so dropping the hint would make things worse. Validation failures and network errors keep it and are not counted: they say nothing about the hint. A plain order is counted by the order guard (D45: 4 per exact set of names in 7 days), so the fallback cannot loop.
- **Shown in plain words.** The second refusal is logged once at WARN (ERROR when the certificate is about to expire) with the next try time, and the status reason adds "the certificate service refused the order that replaces the current certificate twice, so the next try orders a new one without replacing it".

Other clients:
- certmagic (Caddy) leaves `replaces` out on its third attempt whatever the error, "in case the reason the order is failing is only because there is a state inconsistency" (`acmeissuer.go`, `attempts != 2`). Its background renewals (`renewCertOnce`, since #394) never set the attempt count, so for them `replaces` is sent on every try; that gap is the failure the soak hit.
- lego and acmez retry without `replaces` only after `alreadyReplaced`. The lego maintainer declined a fallback for `unauthorized` as "not specific to ARI" and points to `--ari-disable` (lego #2789).
- acme.sh retries at once without `replaces` when the refusal mentions `alreadyReplaced`, `replaces`, `ARI` or `malformed` (Let's Encrypt answers `malformed` or `unauthorized` for some bad hints, ZeroSSL a 401; acme.sh #7280). Pebble's 500 matches none of these.
- Certbot and Traefik do not send `replaces`.
- RFC 9773 section 5: a server SHOULD reject a `replaces` that fails its checks and MUST answer 409 `alreadyReplaced` for an already replaced certificate (registered in section 7.4). It names no error for the other cases and gives clients no retry rule.

Sources, checked 2026-10-31: RFC 9773 sections 4.1, 5 and 7.4; caddyserver/certmagic `acmeissuer.go`, `async.go`, `config.go`, `maintain.go` (`cfd20205`, v0.25.6; issue #361, PR #394); mholt/acmez `client.go` (v3.1.7, `8c3d90a3`, PR #50); go-acme/lego `acme/api/order.go` (`54679098`; issue #2789); acme.sh `_isARIReplacesRejected` (`37d064f7`; issue #7280); certbot `acme/src/acme/client.py`, `acme/src/acme/messages.py` (`138defe9`); Traefik `pkg/provider/acme/provider.go` (`38d53dd0`); Pebble 2.10.1 `ca/ca.go`, `core/types.go`, `wfe/wfe.go`, issue #550 and PR #556.

## D59. A burst of connections to one client waits in line for a data channel instead of getting busy past `limits.max_pending`

Each forwarded connection needs a data channel from its client. When none is ready, up to `limits.max_pending` (512) connections per client wait for one, for at most 10 s, and the server asks the client to open that many more. Until now the 513th got busy at once (`503` for a website, a closed connection for a TCP port), even though the client could open channels in well under a second. A burst to a remote client over a slow link hit this; the benchmark (client `self`) did not.

What others do by default, checked 2026-10-31:

- **frp** asks the client for a work connection when its pool is empty and waits up to `userConnTimeout` (10 s), then gives up with "timeout trying to get work connection". Nothing caps how many wait.
- **rathole** puts visitors in a queue of 2048 (`CHAN_SIZE`). When it is full, its accept loop waits, so new visitors queue in the kernel. A visitor has no deadline while it waits for a channel.
- **chisel** multiplexes over one SSH connection, and a new connection waits up to 35 s (`SSH_WAIT`) for it. Nothing caps how many wait.
- **cloudflared** multiplexes over QUIC and raised its stream limit to the maximum because 100 was too small under bursts.

None of them refuses a burst at once. The owner's rule (2026-10-31): wait like nginx or Caddy would, with no new setting, and no change on the wire, so v0.1.x clients benefit too.

- **The line.** Behind the `max_pending` places, up to three times as many more connections wait in line, so 2,048 per client by default, a quarter of `limits.max_connections_per_client` (8192). Each one is already an accepted, counted connection, so the line adds no new kind of cost. Waiters are served in order. A connection in line that gets no channel within its usual 10 s gets busy, with the same answer, count and log as an immediate refusal before. A connection inside `max_pending` still ends as before when its 10 s pass. Past the line, a connection gets busy at once, as before.
- **The client is asked for no more.** The server still asks for at most `max_pending` channels beyond its ready pool. As each waiter is served, one more is asked for, so the line drains at the client's pace, and a v0.1.x client never sees a larger request than before.
- **Fair share.** One website visitor address gets a fair part of the line, with the D54 rule (an eighth, at least 8, once more than half of the line is used; IPv6 per /64; loopback has no part). As in D54, a service's `bind` port, `burrow visit` and UDP have no part.
- **Ending.** A client that disconnects or that a reload disconnects, or a server that stops, ends every waiter at once (they all go through the session's `close`). A reload that lowers `max_pending` keeps the waiters it has and takes no new ones past the smaller line. A health check waits for a channel within its own check timeout.

Measured on 2026-10-31 on a 10-core VM with the release build: a server and a client on one machine, with every data channel connect delayed by 50 ms through a relay, `limits` at their defaults and the pool at 4/64. N connections were opened at once to a TCP port, each sending 100 bytes and waiting for the echo. Two rounds each, which agreed to within a few percent:

| N | build | served | busy | all done | server peak RSS |
|---|---|---|---|---|---|
| 2,000 | before | 548 | 1,452 | 0.9 s | 21 MB |
| 2,000 | after | 2,000 | 0 | 3.3 s (p99 3.2 s) | 36 MB |
| 4,000 | before | 580 | 3,420 | 1.0 s | 22 MB |
| 4,000 | after | 2,116 | 1,884 | 3.5 s | 37 MB |

The line costs about 10 KB of server memory per waiting connection (14 MB for about 1,500 more waiters). Past the line (N = 4,000), it refuses at once as before. `src/server/session.rs` tests the line, its bound, the deadline answer, the fair part, `close` and a smaller `max_pending` on reload. `tests/integration/connections.rs` sends a burst of 32 connections with `max_pending` 8: all are served, and the build before this change refuses some, over TCP and WebSocket.

## D64. UDP sockets ask for a large receive buffer, as WireGuard does, and burrow keeps no per-socket drop counter

The final v0.2.0 soak lost 113 datagrams in one second. Every one was dropped by the kernel on a socket at Linux's default 208 KiB receive buffer. burrow has no UDP queue that drops: each internal path waits. A back-to-back burst of about 150 datagrams overflows 208 KiB even when the reader keeps up. The old code raised the buffer only below 128 KiB, so on Linux it never did.

- Public UDP ports and visitor UDP forwards ask for 7 MiB, the value wireguard-go uses; quic-go recommends 7.5 MB. Per-peer sockets (the client's sockets to the app, the visitor's SOCKS relay) ask for 256 KiB. A refused size is halved until the system takes it; Linux silently caps it at `net.core.rmem_max` (about 416 KiB by default), and docs/services.md says how to raise it.
- Measured with bursts, 3 runs of 10 s each: drops on burrow's public socket went from 82 to 0 at 150 datagrams a burst, from 842 to 0 at 250, and from 4407 to 908 at 400. Under steady load (1,350 datagrams/s next to busy TCP), UDP p99 was 0.42 ms before and 0.40 ms after, with no loss either time.
- The kernel charges receive buffer only for datagrams that are waiting, so the larger size costs nothing when idle. The worst case is every peer socket full while the tunnel stalls; the kernel's `udp_mem` bounds that total, and WireGuard and quic-go accept the same risk.
- No per-socket drop counter in metrics or status: reading it means OS-specific code in the busiest UDP receive loop. The host-wide `UdpRcvbufErrors` (`nstat`, or node_exporter's `node_netstat_Udp_RcvbufErrors`) already shows it, as it does for nginx's stream proxy.

Sources, checked 2026-11-01: git.zx2c4.com/wireguard-go/tree/conn/controlfns.go; github.com/quic-go/quic-go/wiki/UDP-Buffer-Sizes; nginx.org/en/docs/stream/ngx_stream_core_module.html (`rcvbuf=`, off by default).

## D65. `mode: ip_hash` keeps each visitor address on one client, with weighted rendezvous hashing

The owner asked (2026-11-01) for a mode that keeps a visitor on one client, for apps that keep sessions in memory, while `failover` stays the default: unlike the servers behind nginx or Caddy, a tunnel's clients are often not identical copies, so burrow spreads visitors only when asked. Every common proxy has one: nginx `ip_hash` and `hash $remote_addr consistent`, Caddy `lb_policy ip_hash`/`client_ip_hash`, HAProxy `balance source`. Sticky cookies are not added.

- **The hash.** Each entry (a client and its target) gets a score for the visitor: `weight / -ln(u)`, where `u` in (0, 1) comes from the first 53 bits of SHA-256 over the entry's client, its target and the address. The entries are tried from the highest score down. This is weighted rendezvous (highest random weight) hashing, the logarithmic method of Schindelhauer and Schomaker (2005) as given in Wikipedia's "Rendezvous hashing" (checked 2026-11-01). Caddy's `hostByHashing` uses rendezvous hashing too, without weights (modules/caddyhttp/reverseproxy/selectionpolicies.go, master 6bfeb4f8). Removing or adding an entry moves only the addresses that entry loses or gains, unlike a hash modulo the number of clients; unit tests check the split by weight (3 to 1 within ±2.5 %), that the same address keeps its order, and that removing an entry moves no one else. SHA-256 comes from aws-lc-rs, which burrow already uses for its own digests (D55), and costs well under a microsecond per entry per connection.
- **The address.** For a TCP service it is the TCP peer. For a website it is the visitor as `allow_from` and D54 see it: `X-Forwarded-For` from `web.trusted_proxies`, or the PROXY header from `web.proxy_protocol_from`. IPv6 counts per /64, as in D54, so privacy addresses that rotate inside a /64 stay put; IPv4 counts per address (nginx `ip_hash` uses the first three octets, which puts a whole /24 on one client; Caddy and HAProxy use the whole address).
- **Down clients.** The ranking is applied before the usual grouping, so a client that is offline, failing its health check or set aside drops behind, and that visitor goes to the next entry in its own order; it comes back once the client is up. A connection already open never moves (D25).
- **Scope.** TCP services and websites. Not UDP, which stays failover-only like `balance` and `least_connections`; `validate` refuses it with the same message. Weights apply to `balance` and `ip_hash`.
- **Known weaknesses**, stated in docs/services.md: many visitors behind one NAT or company proxy share an address and so one client, and a visitor whose address changes may move.
- **Per connection today.** A website's visitor connection keeps its app connections for its own address (the per-visitor pool), so all of a visitor's requests already reach one client. Once the shared app pool (C8) picks per request, `ip_hash` picks per request too, with the same result.

## D70. HTTP servers linger after an early answer, as nginx does, so the client gets the answer and not a reset

A server that answers before it has read the whole request (401 for a wrong token, 403, 404, 413, 429, 503) and then closes the socket with request bytes still unread makes the kernel send a TCP reset instead of a clean close (RFC 1122 §4.2.2.13), and bytes that arrive after the close draw a reset too. On Windows a reset drops the answer the client had already received but not yet read; on Linux the client still reads it but sees the reset on its socket. hyper 1.x does not help here: when the service drops a request body unread, hyper reads only what is already buffered and then closes the read side (`poll_drain_or_close_read` in `proto/h1/conn.rs`), and its maintainers leave draining to the application (hyperium/hyper discussion 3113). It failed this way once on Windows CI: the MCP server's 401 for an old token read as nothing.

- Every HTTP/1 server burrow runs closes through one helper, `burrow_io::linger`: the MCP server, the local admin page, the metrics endpoint, the WebSocket transport's refusals, and the web proxy's HTTP/1 connections and tunnel requests. After the last answer it shuts down the write side (the client sees the end of the answer), then reads and drops whatever the client still sends, and closes when the client closes, when nothing arrives for 5 s, after 10 s in all, or after 1 MiB. An upgraded connection is handed over and never lingers, and a connection that ended in an error closes at once as before.
- nginx does the same by default: `lingering_close on`, `lingering_timeout 5s` between reads, `lingering_time 30s` in all. burrow keeps nginx's 5 s, takes 10 s instead of 30 s because its slots are few (8 for MCP) and the client only needs time to read the answer, and adds a 1 MiB cap so an unauthenticated client cannot make it read without end. Go's net/http takes the other route (half-close, then wait 500 ms) and also reads up to 256 KiB of an unread body. No setting: these are fixed, like nginx's defaults that nobody changes.
- HTTP/2 needs no lingering: an early answer resets only its stream, with flow control bounding what the client may still send.
