## Method

```sh
bench/fetch.sh          # downloads pinned rathole, frp and chisel releases and checks their sha256
bench/run.sh            # builds burrow, runs every setup, writes this file
TOOLS='burrow rathole' IDLE_COUNTS=1000 bench/run.sh   # subset
```

- throughput: `iperf3 -c 127.0.0.1 -p <tunnel port> -t 10 -P 1` and `-P 4`, received bits per second.
- latency: one TCP connection, 20000 sequential 64-byte echo round trips (`loadgen latency`), after 200 warm-up round trips.
- p99 under load: the same latency test (5000 round trips) while `iperf3 -P 4 -b 500M` (2 Gbit/s in total, a rate every setup sustains) runs through a second service of the same tunnel; this exposes head-of-line blocking in multiplexed designs without turning into a CPU-saturation contest.
- new connections per second: 32 workers, each opening a new connection, doing one 16-byte echo and closing, for 10 s (`loadgen connrate`).
- memory: `loadgen idle --count N` opens N connections through the tunnel, echoes 4 bytes on each, then holds them; RSS is read from `/proc/<pid>/status` 3 s later.

## Reading the results

- **Encrypted, like for like** (burrow default against rathole with Noise): 2.1x the single-stream throughput, 1.9x with 4 streams, 2.2x the new connections per second, lower p99 under load, and 16x less memory with 10k idle connections. rathole's Noise transport (snowstorm) keeps large per-connection buffers, so its memory grows by about 250 KiB per idle connection; burrow allocates buffers only while data flows.
- **AES-GCM** (`cipher: aes-gcm`) adds 77% single-stream throughput over ChaChaPoly on this AES-NI machine, at the same latency and memory.
- **Plaintext against rathole tcp** (both unencrypted): burrow moves 2x the data and uses half the memory, but rathole opens about 7% more connections per second (15.4k vs 14.3k). burrow still authenticates every data channel with a full Noise handshake in plaintext mode, so refilling the pool costs more CPU than rathole's token check. This is the one row where burrow does not beat rathole, and it is deliberate: the secret never crosses the wire in clear text.
- **Multiplexing** (frp with and without `tcpMux`, same code): turning multiplexing off raises frp's throughput (9.3 to 38.3 Gbit/s with 4 streams) and lowers its p99 under load (694 to 425 µs), but drops new connections per second from 10.4k to 2.9k, because every visitor then waits for a fresh TLS connection. burrow's pre-opened pool gets channel-per-visitor latency and throughput without paying that setup cost (13.8k connections/s).
- Everything runs on one 10-vCPU machine, so the tunnel competes with iperf3 and the load generator for CPU. The absolute numbers are higher on separate machines; the ratios are what to compare.
